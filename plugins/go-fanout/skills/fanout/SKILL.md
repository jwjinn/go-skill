# go-fanout — go-review 체인을 병렬 워커로 펼친다

## 왜 이 스킬이 있나

`go-review:go` 는 **한 세션의 완주**를 잠근다. 작업이 서로 독립적인 N개로 쪼개지는데도 한
세션에서 순차로 돌리면 벽시계 시간이 N배가 되고, 한 세션의 문맥에 N개 작업의 세부가 전부
쌓여 뒤로 갈수록 판단이 흐려진다.

그렇다고 서브에이전트(`Agent` 도구)로 쪼개면 **리뷰 체인이 붙지 않는다** — go-review 의
게이트는 Stop 훅이고, 훅은 세션에 걸린다. 서브에이전트는 자기 Stop 훅을 갖지 않는다.

Orca 오케스트레이션의 워커는 **독립된 에이전트 세션**이다. 그래서 워커마다 go-review 훅이
그대로 무장되고, 워커는 자기 계획 파일·자기 리뷰 파일·자기 git 인덱스를 갖는다.

⚠ **`orchestration` 스킬을 대체하지 않는다.** 이 스킬은 그 위에 **go-review 를 얹는 절차**다.
Orca 명령의 정본은 항상 `orca skills get orchestration` 이고, 이 파일은 그것을 인용하지
복사하지 않는다(정본이 둘이면 어긋난다).

## 언제 쓰나 — 네 조건이 다 맞을 때만

| 조건 | 왜 |
|---|---|
| 작업이 **2개 이상**이고 서로 독립 | 하나면 `go-review:go` 로 충분하다 |
| **파일 집합이 겹치지 않는다** | 겹치면 병렬이 아니라 충돌이다(§2 가 이것을 강제한다) |
| **공유 자원에 경합하지 않는다** | 경합하면 병렬성이 먹힌다(§2-b — 실측으로 겪었다) |
| 각 작업이 **리뷰받을 만한 크기** | 두 줄짜리 수정에 리뷰 라운드 고정비를 쓰지 마라 |

⛔ 안 맞으면 쓰지 마라. 특히 **파일 집합이 겹치는 것을 「조심하면 된다」로 넘기지 마라** —
이 레포에서 남의 미커밋 작업을 삼킨 사고가 실측 6회다.

### ⭐ 그 전에 — 이 작업이 정말 **워커**여야 하나

`go-fanout` 은 비싸다(§1 의 곱셈). 아래로 먼저 갈라라:

| 작업의 성격 | 무엇으로 | 왜 |
|---|---|---|
| **조사·분석·대조**(코드를 안 고친다) | **`Agent` 서브에이전트** | 훅이 필요 없다. 싸고 빠르고 병렬 안전하다 |
| **코드를 고치고 그 결과가 리뷰받아야 한다** | **Orca 워커**(이 스킬) | go-review 게이트가 Stop 훅이고, 훅은 **세션에 걸린다** — 서브에이전트는 자기 Stop 훅이 없다 |
| **문서만 고친다** | 대개 서브에이전트 또는 코디네이터가 직접 | 리뷰 라운드가 값을 하는지 먼저 물어라 |

⚠ **실사용에서 틀린 자리에 워커를 쓴 적이 있다**(2026-09-06): 체크리스트 재판정 워커는
문서만 고쳤는데 리뷰 라운드를 한 번 돌렸다. 값이 없지는 않았지만 서브에이전트로 충분했다.
⭐ 판별식: **「이 작업의 산출물이 잘못되면 런타임이 깨지는가」** — 깨지면 워커, 아니면 서브에이전트.

## 0. 선행 확인 (코디네이터 · 착수 전)

```bash
orca status --json                       # 런타임 ready 인가 (⛔ 없으면 이 스킬은 아무것도 못 한다)
orca skills get orchestration            # ⭐ 명령 문법의 정본을 먼저 읽어라

# 이 플러그인과 형제 플러그인의 설치 위치 — **이 문서에서 한 번만 구하고 이후 이 변수를 쓴다**
GF="${CLAUDE_PLUGIN_ROOT}"
for d in "$GF/../go-review" "$GF"/../../go-review/*/; do [ -d "$d" ] && { GR=$(cd "$d" && pwd); break; }; done
sib() { bash "$GR/hooks/_plugins.sh" "$@"; }   # ⭐ 탐색의 정본은 go-review 안에 한 벌뿐이다
GT=$(sib go-tester tester/_config.py)
GC=$(sib go-coder  coder/_config.py)      # ⭐ 구현 위임 — 계획에 「로컬 구현」이 있으면 필요하다

bash "$GR/hooks/doctor.sh"               # go-review 체인이 살아 있나
```

⚠ **경로를 고정 문자열로 적지 마라.** 설치 방식에 따라 이 플러그인이 놓이는 자리가 다르다 —
심링크(`~/.claude/skills/go-fanout`)와 마켓플레이스(`~/.claude/plugins/cache/<마켓>/go-fanout/<버전>`).
2026-09-16 포장 전에는 `~/.claude/skills/...` 가 문서 전체에 박혀 있어서, 마켓플레이스로 받은
사람은 **없는 경로를 치게** 돼 있었다. `sib` 는 두 모양을 다 찾는다(형제 플러그인은 같은 저장소·
같은 마켓플레이스에서 나오므로 언제나 형제 자리에 있다).

- `doctor.sh` 의 **「훅 등록 5/5」** 를 확인해라. 플러그인 `hooks.json` 경로로 등록돼 있으면
  전역이라 **새 워크트리의 워커 세션에도 자동 적용**된다. 프로젝트 `settings.json` 에만 있으면
  워커 워크트리에는 그 파일이 복제되므로 역시 적용된다 — 어느 쪽인지 확인만 해라.
- **워커 중첩 깊이**를 알아라. 기본 1이면 워커는 다시 워커를 띄우지 못한다.
  ⚠ 이것은 `review-loop` 을 막지 않는다 — 리뷰어는 Orca 워커가 아니라 `Agent` 서브에이전트와
  `codex exec` 이다. 헷갈리지 마라.
- 코디네이터 자신의 `.claude/plan-active.md` 가 이 워크트리의 것인지 확인해라
  (`go-review:go` §0 과 같은 판별).
- ⛔⛔ **base 브랜치를 원격에 올려 놨는지 확인해라** (2026-09-15 실측):
  ```bash
  git ls-remote --heads origin "$(git branch --show-current)" | grep . || echo "⚠ 원격에 없다"
  ```
  워커는 `gh pr create --base <네 브랜치>` 를 하는데, **그 브랜치가 원격에 없으면 PR 을
  만들지 못한다**(`Base ref must be a branch`). 그날 워커 하나가 구현·리뷰·커밋·push 를 전부
  마치고 **PR 단계에서 막혔다.** 코디네이터가 `git push -u origin <브랜치>` 한 번이면 풀린다.
  ⚠ **워커에게 push 를 시키지 마라** — 그 브랜치는 네 워크트리가 체크아웃 중이라 네 커밋과 경합한다.

## 1. 코디네이터의 계획에 무엇이 들어가야 하나

이 스킬은 `go-review:plan` → `go-review:go` 안에서 돈다. 코디네이터의 계획에 아래가 없으면
fan-out 하지 마라.

- ⭐ **계획에 `## 병렬 배치` 표가 있어야 한다**(`go-review:plan` §6-c · 2026-09-13 추가) —
  파도 · 워커 · 항목 · **파일 집합(실측)** · 공유 자원. 그리고 `## C — 자원 회수` 두 줄.
  이 둘이 없으면 fan-out 하지 마라 — 「무엇을 병렬로 할지」는 **요구사항을 분석하는 계획 단계**에서
  정하는 것이고(사용자 지시), 실행 중에 정하면 교차를 코드를 연 뒤에 재게 된다.
- **워커별 파일 집합**을 계획에 **명시**한다(`P1-A (파일: a/** b/**)` 형식).
  교집합이 0 임을 착수 전에 확인한다.
- **웨이브**를 나눈다. 뒤 웨이브가 앞 웨이브의 결과에 의존하면 같은 웨이브에 넣지 마라.
- 계획의 **마지막 리뷰는 합본 1회**다(`base main`). 워커들의 자체 라운드와 별개이고,
  앞 단계들의 수정까지 보는 **유일한 두 번째 눈**이라 생략할 수 없다.
- ⛔ **라운드 예산(`budget.sh`)은 2026-09-07 에 폐지됐다**(사용자 결정 — 「저 기능은 빼자」 ·
  fabrix `CLAUDE.md` 「라운드 횟수 예산 폐지」). 종전에 여기 있던 「(N+1)×자리수 · 워커들이 서로의
  예산을 먹는다」 단락은 그 결정 전의 이력이라 지웠다. 라운드 수는 `_scope.py` 가 diff 크기로 정하고,
  「한 단계 = 한 사이클」은 재리뷰 금지가 집행한다. 리뷰 도구 호출 수를 미리 사용자에게 말하는 것은
  여전히 좋은 습관이다 — 실측(워커 4 + 합본 1 · 세 자리 preset): codex **15회**.

## 2. 파일 집합 불교차 — 하드 게이트 ①

fan-out 직전과 통합 직전에 **두 번** 확인한다.

```bash
# 착수 전: 계획에 적은 경로들의 교집합이 0 인가 (사람이 읽고 판단)
# 통합 전: 실제로 안 겹쳤나 (기계가 판정)
for a in "$WT_A" "$WT_B" "$WT_C" "$WT_D"; do
  git -C "$a" diff --name-only origin/main... 
done | sort | uniq -d        # ⭐ 출력이 있으면 겹쳤다
```

- **겹쳤으면 머지하지 마라.** 겹친 파일을 어느 워커의 것으로 할지 정하고, 다른 쪽 변경을
  그 워커에게 `bash "$GF/scripts/coordinator-send.sh" --to dispatch:<id> --body "…"` 로 넘겨 흡수시킨다.
- ⚠ `uniq -d` 가 **빈 출력**이면 성공이 아니라 **아무것도 안 셌을 수도** 있다.
  같은 명령의 `uniq -c | wc -l`(전체 파일 수)을 함께 출력해 탐지기 생존을 증명해라.

---

### ⚠⚠ 파일 집합 불교차가 **의미 불교차**를 뜻하지 않는다 (2026-09-06 실측)

교차 0 을 기계로 확인해도 합본에서 깨지는 것이 둘 나왔다. 둘 다 **다른 파일에 있는 계약**이었다.

| 무엇이 | 어떻게 드러났나 | 게이트가 왜 못 잡았나 |
|---|---|---|
| **소비자의 폐쇄 어휘** | W-E 가 `envoy-dataplane.yaml` 의 `guard_types` 에 세부 유형(`"rrn"`)을 실었다. 그 필드를 읽는 **세 파일**(glue capture · langfuse client · audit clickhouse)이 `jailbreak\|pii\|secrets\|toxicity` 화이트리스트를 공유한다 ⇒ PII 차단이 증적 요약에서 **「0건」으로 조용히** 남는다 | 그 세 파일은 아무 워커의 집합에도 없었다. **읽기만 하는 파일은 교차 판정에 안 나온다** |
| **생성물의 환경 의존** | W-B 의 `--check` 가 합본 워크트리에서 exit 1 을 냈다. 원인은 드리프트가 아니라 `web/node_modules` 부재로 npm 절이 「미측정」으로 재생성된 것 | 파일은 안 겹쳤다. **탐지기가 환경에 의존한다**는 것은 파일 목록에 안 나타난다 |

⇒ 코디네이터가 §1 에서 워커 스펙을 쓸 때 **파일 집합과 함께 「이 워커가 값을 넣는 필드를
누가 읽는가」를 한 줄 적어라.** `grep -rn '<필드명>'` 한 번이면 나온다. 그리고 워커
프리앰블의 「네 파일 집합 밖을 고치지 마라」 뒤에 이 문장을 붙여라:

> ⭐ 다만 **네가 값을 넣는 필드를 누가 읽는지는 반드시 확인해라**(`grep`). 읽는 쪽에
> 폐쇄 어휘·화이트리스트·타입 스위치가 있으면 그것이 계약이다. 어기면 조용히 틀린다 —
> 고치지는 말고 **코디네이터에게 물어라**(집합을 넓힐지 값을 맞출지는 코디네이터 판단이다).

⭐ 실사용에서 **정본이 이미 있었다** — glue 주석이 2026-07-30 에 「카테고리는 `guard:pii`
하나, 세부는 `pii:rrn`」이라고 정해 뒀는데 새 코드가 그것을 몰랐다. 즉 이 부류는 「정본이
둘」이 아니라 **「정본이 있는데 안 쓰인다」**의 병렬 버전이다.

## 2-b. 공유 자원 경합 — **두 번째 하드 게이트** (2026-09-06 실측으로 추가)

파일이 안 겹쳐도 **같은 자원을 두고 다투면 병렬이 아니다.** 나눠 놓고 한 줄로 서게 된다.

### ⛔ 실제로 겪은 일

워커 넷이 각자 `docker build --platform linux/amd64` 를 돌렸다. arm64 맥에서 amd64 는
**에뮬레이션**이라 메모리를 크게 먹는데, colima VM 이 **CPU 2개·메모리 2GiB** 였다
(호스트는 10코어·16GiB). VM 이 버티지 못하고 죽었고 **넷이 동시에 멈췄다.**
`colima status` 는 "Running" 인데 소켓만 죽어서 「살아 있는데 안 된다」로 보였다.

⭐ 더 중요한 것: **VM 을 키워 재개한 뒤에도 빌드는 사실상 순차였다.** 논리적으로만 병렬이었고
벽시계 이득은 거의 없었다. 게이트 작업(도커를 거의 안 쓰는 워커)만 진짜 병렬이었다.

### 착수 전에 재라 — 짐작하지 마라

워커의 완료 조건에 **빌드·테스트·라이브 호출**이 있으면 그 자원의 용량을 **먼저 재고**
워커 수와 대조해라.

```bash
# 컨테이너 빌드가 있는가
docker info --format 'cpus={{.NCPU}} mem={{.MemTotal}}' 2>/dev/null || echo "도커 없음"
sysctl -n hw.ncpu; sysctl -n hw.memsize        # 호스트(맥)
colima list 2>/dev/null                         # VM 이면 그 크기가 진짜 한도다

# CI 러너에 의존하는가
gh api repos/<owner>/<repo>/actions/runners --jq '.total_count'

# 레지스트리·클러스터를 공유하는가 → 다른 작업이 지금 쓰고 있는지 본다
kubectl get deploy -A -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.conditions[?(@.type=="Progressing")].lastUpdateTime}{"\n"}{end}' | sort -k2 | tail -5
```

| 자원 | 무엇을 확인 | 안 맞으면 |
|---|---|---|
| **도커 VM** | 워커 수 × 동시 빌드 1개가 들어가나. amd64 에뮬레이션이면 워커당 **2GiB 이상**을 잡아라 | VM 을 먼저 키우거나 웨이브를 나눠라 |
| **CI 러너** | 러너 수 < 워커 수면 PR CI 가 큐에 선다 | 벽시계 이득을 그만큼 깎아서 계산해라 |
| **레지스트리·클러스터·그림자 스택** | **다른 작업이 지금 쓰고 있는가** | 쓰고 있으면 그 자원을 쓰는 검증은 워커에서 빼고 코디네이터가 로컬로 대체해라 |

⚠ **그림자 스택은 특히 조심해라.** 실측(2026-09-06): 그림자 스택에 롤아웃하려다 보니
**다른 워크트리가 몇 분 전 갱신해 쓰고 있었고**, 게다가 그 스택에는 검증하려던 가드가
아예 없었다. 계획을 그대로 밀었으면 남의 검증을 깨뜨리고도 원하는 것을 못 쟀다.

### 워커 프리앰블에 반드시 넣어라

```
⚠ 빌드는 **한 번에 하나씩** 돌려라(`docker build` 를 병렬로 띄우지 마라).
   워커가 N개라 각자 하나씩만 돌려도 동시 N개다.
⚠ 공유 자원(도커 데몬·클러스터·레지스트리)이 죽으면 **네 판단으로 재시작하지 마라** —
   `orca orchestration ask` 로 코디네이터에게 물어라. 다른 워커의 작업을 함께 죽인다.
```

⭐ 이 두 줄이 실제로 값을 했다 — 워커 둘이 도커 데몬이 죽었을 때 각자 「공유 자원이라
내 판단으로 재시작하지 않겠다」며 물어 왔다. 그 판단이 옳았다.

## 3. 워커를 띄운다

```bash
orca orchestration run-create --objective "<코디네이터 계획의 목표 한 줄>" --json
orca orchestration task-create --spec "<워커 A 의 작업 — 아래 §4 프리앰블 전문>" --json
orca orchestration task-create --spec "<워커 B …>" --json
# … 전부 만든 뒤 ⭐ 한꺼번에 시작한다(하나 띄우고 기다리지 마라)
orca orchestration worker-start --task <task_a> --worktree new-child --name sec-go-images \
  --agent claude --setup run --json
```

**워크트리 선택**:

| 상황 | 선택 | 왜 |
|---|---|---|
| 기본 | `--worktree new-child --name <브랜치 슬러그>` | 계획·리뷰 파일과 git 인덱스가 자연히 분리된다 |
| 작업이 코디네이터의 미커밋 파일에 의존 | `--worktree current` | ⚠ 그러면 계획 파일을 공유한다 — `CLAUDE_PLAN_FILE` 을 워커마다 다르게 주지 않는 한 게이트가 충돌한다 |
| 완전히 무관한 작업 | `--worktree new-top-level` | 부모 계보를 만들지 않는다 |

⭐ **`--setup run` 을 빼지 마라.** 레포 setup 훅(의존성 설치 등)이 안 돌면 워커가 테스트를
못 돌리고, 그러면 완료 조건을 못 채운다.

⭐ **`worktree create` 는 기본 베이스가 레포 기본 브랜치**다. 피처 브랜치에서 파생시키려면
`--base-branch` 를 명시해라 — 안 하면 워커가 「내 브랜치 위에서 시작한 줄 알았는데 main
이었다」를 겪는다.

**계획 초안 시드**: 워커가 `go-review:go` 를 부르려면 그 워크트리에 `.claude/plan-draft.md`
가 있어야 한다(없으면 워커는 §0-b 경로 ③ 에서 멈춘다). `worker-start` 응답의 워크트리
경로에 코디네이터가 **미리 써 넣어라**:

```bash
WT=$(orca orchestration worker-show --dispatch <id> --json | jq -r '.result.worker.worktree_path')
# 그 워커 몫만 잘라낸 초안을 $WT/.claude/plan-draft.md 로 쓴다
```

### ⛔⛔ 테스트 위임을 쓸 계획이면 — **워커는 스스로 켤 수 없다** (2026-09-15 실측)

계획의 Q-T 에서 「로컬 모델을 쓴다」를 받았어도, **워커 워크트리에서는 그것이 이어지지 않는다.**
그 승인은 옵트인 파일로 기록되는데, 그 파일을 만들려면 사람에게 물어야 하고 **워커는 사람과
연결되어 있지 않다.** 실측: 그날 워커는 위임을 한 번도 쓰지 않고 자기가 직접 테스트를 썼다 —
설계대로 「안 쓰는 쪽」으로 닫힌 것이고, 그것 자체는 안전하다. 다만 **계획이 기대한 절감이 0** 이다.

⛔ **옵트인을 미리 넣어도 소용없다.** 그 기록은 계획의 **범위 해시**에 묶이는데, 워커는
시드받은 초안을 **자기가 다시 쓴다**(실측 — 워커가 실측 근거를 넣어 다시 썼다). 그 순간 해시가
달라져 무효가 된다(`optin_stale`).
⚠ 2026-09-17 부터 그 해시는 **체크박스 상태를 뺀** 값이다 — 진행하며 항목을 닫는 것만으로는
무효가 되지 않는다. 그래도 워커가 본문을 다시 쓰면 범위가 달라진 것이라 무효가 맞다.

⇒ 남는 경로는 하나다. **워커 폴더의 구성값을 `on` 으로 둔다.** `plan-draft.md` 를 시드하는
**같은 자리에서** 함께 해라:

```bash
python3 - "$WT" <<'PY'
import io, json, sys
p = sys.argv[1] + "/.claude/tester/config.json"
try:
    d = json.load(io.open(p, encoding="utf-8"))
except Exception:
    raise SystemExit("구성 파일이 없다 — 이 프로젝트는 go-tester 를 쓰지 않는다")
d["enabled"] = "on"
d["_왜 on 인가"] = ["워커는 사람에게 물을 수 없어 옵트인을 만들지 못한다.",
                   "코디네이터가 계획 단계에서 받은 승인을 여기로 옮긴 것이다.",
                   "⚠ 워커 폴더에만 둔다 — 레포에 커밋된 구성은 ask 그대로다."]
json.dump(d, io.open(p, "w", encoding="utf-8"), ensure_ascii=False, indent=2)

```

⚠⚠ **레포에 커밋된 구성을 `on` 으로 바꾸지 마라.** 그러면 그 레포의 모든 세션이 묻지 않고
켜진다 — 「기본은 안 씀」이 통째로 깨진다. 고치는 것은 **워커 폴더의 사본**뿐이고, 그 폴더는
파도가 끝나면 회수된다.

⚠ **워커 프리앰블에 한 줄을 넣어라** — 구성만 켜면 워커는 「쓸 수 있다」와 「어디서 쓰나」를
잇지 못한다:

> 테스트 위임이 켜져 있다. 계획에 `위임 가능 (full)` 또는 `일부 위임` 이라 적힌 항목에 닿으면
> `$GT/tester/tester.sh` 를 부르고(위 §0 의 `sib`), 그 밖에는 네가 직접 써라.
> 「일부 위임」이면 **구현을 먼저 끝내고 테스트만** 넘겨라(자식은 소스를 고칠 수 없다).

### ⛔⛔ 구현 위임(go-coder)도 계획에 있으면 — **따로 켜야 한다** (2026-09-17 추가)

⚠ 위 절차는 **테스트 위임 전용**이다. `go-coder` 는 다른 도구이고 구성 파일도 옵트인도
따로다(`.claude/coder/config.json` · `.claude/coder/opt-in.json`). 종전에 이 문서는 go-coder 를

계획의 격자 판정에 「로컬 구현」이 있는데 이 절을 건너뛰면 그 항목은 전부 세션 모델이 맡는다.

⛔ **구성 파일이 없으면 거기서 멈춰라.** `profile` 이 비어 있으면 `_config.py` 가
`no_profile` 로 닫고, 그 상태에서는 「쓴다」고 답해도 돌지 않는다. 프로파일 이름과 그것이
가리키는 모델을 **계획 단계에서** 확인해 두어라.
⚠ codex 프로파일은 `~/.codex/config.toml` 안에만 있는 것이 아니다 — 별도 파일
(`~/.codex/<이름>.config.toml`)로 사는 경우가 있고, 그것을 모르면 「없는 프로파일」로 오진한다
(2026-09-17 실측).

⚠ **워커 프리앰블에 한 줄을 넣어라**:

> 구현 위임이 켜져 있다. 계획에 `로컬 구현` 이라 적힌 항목에 닿으면 `$GC/coder/coder.sh` 를
> 부르고, 그 밖에는 네가 직접 구현해라. ⛔ **부르기 전에 그 항목의 게이트가 붉은지 확인해라**
> — 이미 초록이면 rc 67 로 거부된다(고칠 것이 없으면 「고쳤다」를 판정할 수 없다).
> `--targets` 와 `--gate` 는 **계획이 정한 것을 그대로** 넘겨라. 네가 넓히지 마라.

⚠⚠ 테스트 위임과 **한 번에 묻지 마라.** 구현을 넘기는 것은 테스트를 넘기는 것보다 큰 결정이고,
한 번의 「쓴다」로 둘이 켜지면 사람이 무엇에 답했는지 모르게 된다. `/go` §0-d 와 §0-e 가 그
둘을 따로 묻는 이유가 이것이다.

### ⚠ 첫 파도는 **한 워커만** 켜라 — 긴 작업의 동시성은 미측정이다

로컬 모델 게이트웨이 뒤의 GPU 는 보통 **하나**이고, 워커 N 명이 각자 부르면 전부 그리로 간다.
실측된 것은 짧은 호출뿐이다(동시 12까지 실패 0 · 지연만 2.4초 → 10.0초). 실제 테스트 작업의
동시성은 표본이 없다.

- 첫 파도에서 **한 워커만** 켜고 그 원장(`docs/리뷰-이력/tester.jsonl`)을 본다.
- rc 0 이고 벽시계가 단독 실행과 크게 다르지 않으면 다음 파도에서 넓힌다.
- 세마포어 상한(기본 4)을 넘으면 대기하다 rc 70 으로 폴백한다. **망가지지는 않지만 벽시계가
  는다** — 그것이 넓히기 전에 재야 하는 이유다.

⚠ 시드하는 초안에도 **`## 결정 필요(승인 전)` 절이 있어야 한다.** 워커에게 물을 것이 없으면
`없음 — 코디네이터가 사전에 닫았다` 라고 적어라. 절이 없으면 워커의 `go-review:go` 가
「안 적었다」와 「없다」를 못 갈라 되돌린다.

## 4. 워커 프리앰블 — Task spec 에 그대로 넣는 템플릿

Orca 가 이 앞에 자기 lifecycle 프리앰블(`worker_done` 규약 등)을 붙인다. 아래는 **그 뒤에
오는 우리 몫**이다.

⛔⛔ **spec 의 첫 줄을 「한국어 한 줄 요약 · 워크트리 이름」으로 시작해라**(2026-09-18 사용자 지시:
「워커 F가 내가 보기엔 무엇인지 보기 어렵거든. 무슨 워크트리에 있다 라고 하던가」).

**왜**: Orca 의 워커 목록은 워커가 **끝나기 전까지** `worker_done` 의 subject 를 못 보여준다.
그 자리를 spec 에서 만든 **자동 요약**이 채우는데, 우리 템플릿은 첫 줄이 늘 「너는 병렬 워커다 —
규약」이라 요약이 본문 아무 데서나 뽑히고 **영어로 나오기도 한다.** 실측(2026-09-18): 끝난 워커
넷은 한국어로 「⑪⑫ 상황판 …」처럼 읽히는데 **진행 중인 하나만** "Storage inventory dashboard
implementatio…" 였다. 사람이 목록을 보고 **무엇을 하는 워커인지 가릴 수 없다.**

⇒ 첫 줄을 이렇게 고정한다. 그러면 자동 요약이 그 줄을 집는다:

```markdown
# [<워크트리 이름>] <한국어 한 줄 — 무엇을 하는 워커인가>
```
예: `# [storage-inventory] ⑮ 저장소 인벤토리 — 어디에·얼마나·언제까지`
⚠ **워크트리 이름을 대괄호로 앞에 둬라.** 목록이 좁아 줄 끝이 잘리므로 뒤에 두면 안 보인다.

```markdown
# [<워크트리 이름>] <한국어 한 줄 — 무엇을 하는 워커인가>

## 너는 병렬 워커다 — 규약

작업 위치: <워크트리 절대경로> (브랜치 <브랜치명> · base <base>)

### ⚠ 시작할 때 — 초안이 없으면 **기다렸다 다시 읽어라** (2026-09-15 · 3/3 재현)

`worker-start` 가 세션을 **즉시** 띄우는데 코디네이터가 초안을 써 넣는 것은 그 응답을 받은
뒤다. **처음 읽으면 없다.** 그날 워커 셋이 전부 이 자리를 밟았고, 하나는 코디네이터에게 물으며
5분 35초를 기다렸고 다른 하나는 **스스로 범위를 재구성하려 했다.**

⇒ 없으면 **60초 간격으로 3회까지** 다시 읽어라. 그래도 없으면 그때 물어라.
⛔ **없다고 네가 범위를 재구성하지 마라** — 그렇게 만든 범위는 승인받은 범위가 아니다.

### 절차 (이 순서를 지켜라)
1. 그 워크트리의 `CLAUDE.md`/`AGENTS.md` 를 **먼저 읽어라**. 슬라이스를 건드리면 그
   디렉토리의 `AGENTS.md` 도 읽어라. ⭐ 프론트를 고치면 `web/DESIGN.md` 도.
2. `.claude/plan-draft.md` 가 시드돼 있다(위 대기 규약 참조). 스킬 `go-review:go` 를
   **범위 전부**로 불러 승인하고 착수해라.
3. 구현 → 그 워크트리의 게이트를 돌린다(`CLAUDE.md` 의 「빌드·테스트·린트」 그대로).
4. 스킬 `go-review:review-loop` 을 **1회** 돌린다. must_fix 를 반영한다.
   ⛔ **재리뷰하지 마라** — 한 작업 = 한 사이클이다.
5. 커밋(**경로 지정** `git add <경로>` · 메시지는 파일로 `-F`)  → 브랜치 push → `gh pr create`.
6. 종료 보고 7절을 `.claude/go-report.md` 에 쓴다(`go-review:go` §7 형식).

### 하지 마라
- ⛔ **사용자에게 묻지 마라.** 너는 사용자와 연결돼 있지 않다. **막혀서 답이 있어야 진행되면**
  `orca orchestration ask --question "<질문>" --options "a,b" --timeout-ms 600000 --json` 로
  **코디네이터에게** 물어라. 답이 올 때까지 그 질문에 의존하지 않는 항목을 먼저 해라.
- ⭐⭐ **막히지는 않았는데 코디네이터가 알아야 하는 것**은 `ask` 가 아니라 이것이다:
  `orca orchestration send --type escalation --subject "<한 줄>" --body "<무엇을 발견했나>" --json`
  예: 네 집합 밖에서 결함을 봤다 · 완료 조건이 현실과 다르다 · 다른 워커와 부딪칠 것 같다 ·
  전제가 틀렸다. 종전에는 채널이 `ask` 뿐이라 이런 것을 **말할 자리가 없었고**, 워커는 혼자
  판단하거나 종료 보고에만 적었다(그러면 파도가 끝난 뒤에 읽힌다).
  ⚠ `ask` 는 너를 멈춰 세우고 `escalation` 은 멈추지 않는다. 진행하면서 알려라.
- ⛔⛔ **그리고 진행하면서 `orca orchestration check --json` 을 불러라**
  (블로킹 아님 · 온 것만 가져온다). 코디네이터의 답은 **네가 부를 때만 도착한다.**
  부르는 시점은 둘이다: **한 항목을 끝낼 때마다**, 그리고 **터미널에 「코디네이터 메시지가
  왔다」가 찍히면 즉시**(코디네이터의 래퍼가 그렇게 깨운다).
  ⛔⛔ **앞 배치를 처리했으면 다음 호출에 `--ack <delivery_id>` 를 붙여라.** 그 값은 **앞
  응답이 준다.** `--ack` 를 **값 없이** 쓰면 CLI 가 `--ack requires a value` 로 **명령 전체를
  거부**하고, 그러면 읽음 표시가 갱신되지 않아 같은 배치가 계속 재생된다(2026-09-17 실측 —
  코디네이터가 보낸 12건이 **한 건도 읽히지 않았다**). 정본 문법은 `orca skills get
  orchestration` 이 갖고 있다.
  ⚠ 실측(2026-09-15): 워커가 보안 변경을 두 번 물었고 코디네이터가 두 번 답했는데, 그 워커의
  완료 보고는 「**답을 받지 못해** 결정은 넘겼습니다」였다. 막히지 않으면 안 부르는 것이 설계라
  그 규약이 없으면 답이 도착하지 않는다.
- ⛔ **네 파일 집합 밖을 고치지 마라.** 아래 목록이 전부다. 밖에서 문제를 발견하면
  고치지 말고 종료 보고 ⑦에 적어라(다른 워커가 그 파일을 동시에 고치고 있다).
- ⛔ `git add -A` · `git stash`(태그 없이) · `git reset --hard` 금지.
- ⛔ 머지하지 마라. PR 까지가 네 몫이다.
```

### ⛔⛔ 화면 작업이면 **목업 경로를 파일로 적어라** (2026-09-15 실측)

사용자가 목업을 고르는 프로젝트에서, 지시서에 **결정 내용만 적고 그것이 어느 파일인지 안 적었다.**
그래서 워커들이 목업을 모르고 시작했고 하나는 「대응표를 못 찾겠다」고 물었다.

⇒ 화면을 건드리는 워커의 지시서에 **반드시 넣어라**:

```markdown
### 네 목업 — 이것이 정본이다
docs/UIUX/mockups-<화면>-<날짜>/1-<화면>-대조.html   ← 화면 확정본(고른 안)
docs/UIUX/mockups-<화면>-<날짜>/대응표.tsv
docs/UIUX/mockups-<화면>-<날짜>/부품-처분표.tsv
docs/UIUX/mockups-<화면>-<날짜>/_check.mjs           ← 그 목업 자체의 검사기
⚠ 대응표만 보면 「무엇을」은 알아도 「어떤 순서로」는 모른다. **HTML 을 먼저 열어라.**
```

⚠⚠ **행수를 계획서에서 베끼지 마라.** 그날 계획의 세 숫자가 **전부 틀렸다**(85→실제 111 ·
138→169 · 117→133). 이전 라운드 표의 행수를 검증 없이 옮긴 것이었다.
⇒ 지시서에는 **경로만** 적고 「그 파일을 열어 네가 세라 · 완료 조건은 숫자가 아니라 **보류 0**」
이라고 써라.

⭐ **목업은 각자 자기 디렉토리 안에 대응표를 갖는다.** 공용 `docs/UIUX/대응표/` 만 보고
「없다」고 결론짓지 마라 — 그날 코디네이터가 그렇게 해서 「그 화면 목업은 없다」고 **확정 진술**을
했고, 전수 검색하니 있었다(「탐지기를 먼저 의심하라」).

### ⭐ 「집합 밖으로 번진다」는 질문이 **가장 많이 온다** (2026-09-15 · 8건 중 6건)

워커가 자기 파일만 고치려는데 그 변경이 밖으로 번지는 경우다. 실측된 부류 셋:

| 부류 | 예 | 판단 기준 |
|---|---|---|
| **지우면 죽는 코드** | 라우트를 지우니 클라이언트 함수·테스트·권한 선언·주석이 죽었다(한 건에서 **다섯 자리**) | 겹침 0 이면 **워커가 함께 지운다**. 남기면 다음 사람이 「의도적」으로 읽는다 |
| **같은 값을 두 곳이 쓴다** | 지어낸 라우팅 값을 화면 둘이 쓴다 · 역할 개수를 테스트 둘이 잠근다 | 겹침 0 이면 **둘 다 고친다**. 하나만 고치면 게이트가 붉거나 절반만 지켜진다 |
| **내 변경이 남의 결함을 깨운다** | replicas 를 2 로 올리니 잠자던 도메인 설정 결함이 활성화 | ⛔ **반드시 함께 고친다.** 「주석 경고만」으로 끝내지 마라 |

⇒ **코디네이터의 답은 거의 항상 「겹침을 재고, 0 이면 집합을 넓힌다」다.** 재는 법:
```bash
grep -l '<파일명>' <각 워커 지시서>   # 0건이면 안전
gh pr view <이미 끝난 워커 PR> --json files --jq '.files[].path' | grep '<파일명>'
```
⚠ **「조심하면 된다」로 넘기지 마라** — 겹치는데 넓히면 그때가 충돌이다.

## 5. 코디네이터의 대기 루프

```bash
# 첫 호출 — ack 할 앞 배치가 없다
orca orchestration check --wait --types worker_done,escalation,question \
  --timeout-ms 900000 --json

# 그 배치를 전부 처리한 뒤 — 앞 응답이 준 delivery_id 로 ack 하면서 다음을 받는다
orca orchestration check --ack <delivery_id> --wait \
  --types worker_done,escalation,question --timeout-ms 900000 --json
```

- **타임아웃은 실패가 아니다.** 코딩 작업은 15~60분이 예사다. `{count:0}` 이면 다시 기다려라.
  워커를 죽이지 마라.
- ⛔⛔ **`--ack` 는 값을 받는다.** `--ack <delivery_id>` 이고 그 값은 **앞 응답이 준다.**
  값 없이 쓰면 CLI 가 `--ack requires a value` 로 **명령 전체를 거부**한다 — 메시지를 못
  받는 것이 아니라 **명령이 실패한** 것이라, JSON 을 파싱하면 `count: None` 이 나와
  「메시지 없음」처럼 보인다. 2026-09-17 에 그것을 밟았고 코디네이터→워커 12건이 전부
  미읽음으로 남았다.
- ⭐ ack 는 **그 배치의 메시지를 전부 처리한 뒤에** 한다. 안 하면 같은 배치가 계속 재생되고,
  Stop 훅이 그것으로 턴을 막는다.
- ⚠⚠ **이 문법의 정본은 `orca skills get orchestration` 이다.** 이 파일은 그것을 인용할 뿐
  다시 쓰지 마라 — 위 결함이 정확히 그렇게 생겼다(정본을 복사해 옮겨 적다가 인자를 잃었다).

### ⛔⛔ 2026-09-16 개정 — **`check` 가 기본이다. `worker-list` 폴링으로 대신하지 마라**

종전 문안은 「블로킹이 싫으면 `worker-list` 로 폴링하라」였다. 그 한 줄이 이 체인에서 가장
비쌌다. 실측(인박스 695건):

| 무엇 | 수 |
|---|---|
| worker_done 미읽음 | 40건 중 13 |
| escalation 미읽음 | 15건 중 8(한 run 은 7/7) |
| worker_done 미소비 | 34 · run 7 중 6 에서 소비 0 |

`worker-list` 는 **상태만 보여주고 메시지를 안 보여준다.** 워커는 말했고 코디네이터는 듣지
않았다. 그리고 `inbox` 도 해법이 아니다 — 그것은 **읽음 표시를 바꾸지 않는다**(실측). 인박스를
소비하는 명령은 `check` 하나다.

```bash
# 기다려도 될 때(기본) — 메시지가 오면 즉시 깨어난다
orca orchestration check --wait --types worker_done,escalation,question \
  --timeout-ms 900000 --json

# 그 사이 자기 단계를 진행해야 할 때 — 같은 명령을 **wait 없이** 주기적으로
orca orchestration check --json

# 앞 배치를 처리했으면 그 delivery_id 로 ack 하면서 다음을 받는다(값을 빠뜨리면 명령이 거부된다)
orca orchestration check --ack <delivery_id> --json
```

- **비블로킹이 필요해도 `check` 를 써라.** `--wait` 만 빼면 된다. 바꿀 것은 명령이 아니라 대기다.
- `worker-list` 는 **상태 보조**다(누가 도는가·핸들은 무엇인가). 메시지 확인 수단이 아니다.
- `inbox` 는 **읽지 않고 들여다보는** 자리다. 세어 보는 데는 쓰되, 그것으로 「확인했다」고 하지 마라.
- Stop 훅 `coordinator-inbox-gate.sh` 가 안 읽은 완료 보고·에스컬레이션·미답 질문으로 턴 종료를
  막는다. 그 문구가 가리키는 해법도 `check --ack <delivery_id>` 다.

⚠⚠ **없는 명령을 부르면 CLI 가 usage 를 내는데, 그 출력을 JSON 으로 파싱하면 「0건」이 된다.**
2026-09-15 에 `message-list`(없는 명령)를 불러 「질문이 안 온다」로 **오진**했고 문서에 도구
결함으로 적기까지 했다. `orca orchestration --help` 로 명령이 실존하는지 먼저 확인해라 —
**「탐지기를 먼저 의심하라」의 교과서적 사례다.**

### ⭐⭐ 그리고 그것을 **훅으로 잠가라** — 규율로는 안 된다

절차는 이미 있었고(위 대기 루프) 내가 안 따랐다. 그래서 **Stop 훅**으로 만들었다:
`coordinator-inbox-gate.sh` — 안 읽은 `worker_done`·`escalation` 이나 답 없는 `question` 이 하나라도 있으면 **턴 종료를 거부**한다(이 세션이 관여한 run 만 · 2026-09-16 에 `worker-question-gate.sh` 에서 개명하며 축이 셋이 됐다).

**훅 본체는 이 플러그인에 있고 설치가 곧 등록이다** — `hooks/coordinator-inbox-gate.sh`
(대조군 `hooks/coordinator-inbox-gate.test.sh` — 검사 수는 그 출력의 마지막 줄이 정본이다).
`hooks/hooks.json` 이 Stop 에
붙이므로 프로젝트마다 손으로 넣을 것이 없다.

```bash
bash "$GF/hooks/coordinator-inbox-gate.test.sh" # 마지막 줄이 「실패 0」인지 본다
```

⛔⛔ **프로젝트로 복사하지 마라.** 2026-09-16 포장 전에는 이 절이 「복사해 설치한다」였고,
실제로 fabrix 의 `.claude/hooks/` 에 사본 둘이 생겨 정본이 갈릴 자리가 됐다. 사본은 워커
워크트리로 그대로 퍼지고, 고칠 때 한쪽만 고치면 다음 레포가 낡은 것을 받는다 — 이 파이프라인이
잡으려는 「정본이 둘」 그 자체다. 이미 복사본이 있으면 **지우고 등록 줄도 함께 빼라**(안 그러면
같은 게이트가 두 번 돈다).

판정: `type=question` 인 메시지 중, 같은 `thread_id` 를 가진 답변(`type=status` ·
`to_handle` 이 `dispatch:`)이 없는 것.

⭐ **만든 지 두 시간 만에 여덟 건을 잡았다.** 그중 셋은 코디네이터 계획의 실질적 결함이었다.
⚠ 원칙 셋: **훅 고장은 통과**(orca 없음·JSON 깨짐) · **세션당 상한**(기본 8) ·
**판정 불가는 통과**(계획 완주 게이트와 반대다 — 막는 대상이 「내가 놓친 질문」이지
「내가 안 한 일」이 아니라서, orca 를 안 쓰는 세션을 멈추면 안 된다).

⚠⚠ **이 훅으로도 못 잡는 것이 하나 있다** — 「코디네이터가 답했나」는 보지만
**「워커가 그 답을 받았나」**는 못 본다. 후자가 실제 결과를 정한다. 그래서 프리앰블의
`check` 폴링 규약(§4)이 함께 있어야 한다. 둘 중 하나만으로는 닫히지 않는다.
- ⚠ `check --wait --json` 은 stdout 에 JSON 하나, stderr 에 keepalive 를 낸다.
  **스트림을 합쳐 파서에 넣지 마라**(`2>&1 | jq` 는 깨진다).
- **Delivery 안의 메시지를 전부 처리한 뒤에** `--ack <delivery_id>` 해라(값을 빠뜨리지 마라).

### ⚠⚠ 메시지는 워커가 `check` 할 때만 도착한다 — 규약은 **프리앰블에** 넣어라

`orca orchestration send --to dispatch:<id>` 는 **inbox 메일**이다. 워커가 다음 번
`orchestration check` 를 부를 때 도착하고, 워커는 자기 일이 막히지 않으면 그것을 부르지 않는다.

⛔⛔ 실측(2026-09-16): 코디네이터가 워커에게 보낸 단독 `send` **55건 중 54건이 미읽음**이었다.
98%가 도착하지 않은 것이다. 같은 기간 `reply` 는 600초 안에 보낸 57건이 전부 읽혔다.
차이는 그때 워커가 무엇을 하고 있었나다 — `reply` 는 `ask` 로 막혀 기다리는 워커에게 가므로
반환값으로 즉시 닿는다.

⛔ 실측(2026-09-06): 「`docs/리뷰-이력/` 을 커밋하지 마라」를 넷에게 보냈는데 **둘은 이미
커밋한 뒤에 받았다.** 그래서 머지 때 그 세 파일이 충돌했다(다행히 append-only 라 이어 붙여
해결했지만, 코드였으면 훨씬 비쌌다).

⇒ 둘을 함께 한다. **작업 규약은 Task spec(프리앰블)에 처음부터 넣고**, 도중 메시지는
**래퍼로 보낸다**(inbox 에 남기고 터미널로 깨운다 · 사용자 결정 2026-09-16):

```bash
bash "$GF/scripts/coordinator-send.sh" --to dispatch:<id> --subject "…" --body "…"
#   ① orchestration send   — 기록·스레드·읽음 추적이 여기 남는다
#   ② worker-show          — 그 워커의 터미널 핸들
#   ③ terminal send --enter — 「인박스를 봐라」 한 마디(본문은 넣지 않는다)
# --no-nudge 로 ③ 생략 · --wait-read <초> 로 읽혔는지 확인 · --nudge-only 로 ① 생략
```

⚠ 터미널에 **본문을 타이핑하지 마라.** 터미널에 넣은 글자는 기록도 스레드도 읽음 추적도
남기지 않는다. 터미널이 하는 일은 깨우기 한 가지다.
⚠ 도중 메시지로는 「이미 그 일을 한 워커」를 되돌리지 못한다. 값을 하는 것은 두 경우다:
① 워커가 `ask` 로 물어서 **기다리고 있을 때**의 답 ② 아직 그 단계에 닿지 않은 워커에게 주는 정보.

### `question` 이 오면

**계획 안에 답이 있으면** 그것으로 답한다. ⭐ 보내는 자리는 **래퍼 하나**다:

```bash
bash "$GF/scripts/coordinator-send.sh" --reply <msg_id> --body "<답>"
```

래퍼가 inbox 로 답하고, 원 질문이 오래됐으면(기본 600초) **터미널로 깨우기까지** 한다.
실측: 600초 안에 보낸 `reply` 는 57건 전부 읽혔고, 600초를 넘긴 4건 중 1건은 미읽음이었다.
워커가 그 사이 `ask` 에서 빠져나와 있으면 답은 inbox 에만 쌓인다.

**계획 밖이면** — 사용자에게 묻지 말고 **보수적 기본**(범위를 넓히지 않는 쪽)으로 답한 뒤,
그 사실과 판단 근거를 종료 보고 ⑦에 **반드시** 적어라. 사용자의 검증층은 그 보고다.
⚠ 되돌릴 수 없는 것(외부 발송·데이터 삭제·비용)은 예외다 — 그것은 워커에게 **하지 말라고**
답하고 사람 몫 목록(⑥)에 올려라.

### `worker_done` 이 오면

1. `--report-path` 의 보고서를 읽는다.
2. 완료 조건을 **코디네이터가 다시 판정한다** — 워커의 자기 신고를 그대로 받지 마라.
   완료 조건에 적은 명령을 코디네이터가 직접 돌려 본다.
3. 다음 Task 가 그 워커에게 바로 갈 것이 아니면 `worker-release`:

```bash
orca orchestration worker-release --dispatch <dispatch_id> --json
```

⚠ 타임아웃·heartbeat·질문·에스컬레이션으로 release 하지 마라. 완료 보고에만 한다.
⚠ **실측(2026-09-07): 이 release 가 실제로는 한 번도 안 됐다** — 두 라운드 워커 11개가
전부 `succeeded` 인데 `terminalState: retained` 였다. 코디네이터가 `worker_done` 처리 중에
빠뜨린다. 그래서 §7 의 `cleanup.sh` 가 release 를 **다시** 한다(멱등이라 두 번 해도 안전).

1. **파일 집합 교차 재확인**(§2 두 번째 확인).
2. PR 별 CI 결과를 본다 — ⭐ **초록만 보지 말고 각 게이트가 몇 개를 셌는지** 봐라.

3. **합본 리뷰**(`go-review:review-loop base main`). 워커들의 수정까지 보는 유일한 눈이다.

   ⚠⚠ **「1회」로 계획하지 마라 — 워커가 넷을 넘으면 합본이 상한을 넘는다**(2026-09-06 실측).
   워커 5명의 합본 diff 가 **4,146줄 · 48파일 · 리뷰어 1명당 ~76,400 토큰**이었고
   `_scope.py` 가 상한(`CLAUDE_REVIEW_SPLIT_LINES`, 기본 2000)의 **두 배**라며 나누라고 했다.
   그래서 두 라운드로 갈랐다(1,566줄 / 2,580줄).
   ⇒ §1 의 예산 계산에 **합본을 1 이 아니라 `ceil(예상 합본 줄수 / 상한)`** 으로 넣어라.
   ⭐ 자를 곳은 **크기가 아니라 워커 경계**다. `_scope.py` 는 커밋 경계를 제안하지만 그것은
   크기만 본 것이고, 한 워커의 변경이 두 라운드에 걸쳐 쪼개지면 리뷰어가 그 변경의 의도를

   실측으로 그것이 코디네이터 워크트리의 HEAD 를 해석해 **엉뚱한 커밋 목록**을 제안했다
   (diff 파일 자체는 맞았고 「자를 곳」 제안만 틀렸다). 인자를 빼면 파일만 보고 잰다.

   ⭐⭐ **합본 라운드는 워커 라운드와 다른 모델 계열로 돌려라**(2026-09-06 실사용 근거).

   워커 4명 + 합본이 모두 codex 였던 라운드에서 합본 후보 **7건이 전부 단독 발견**이었고
   합의로 검증된 것이 **0건**이라, 병합자가 7건 모두 코드를 열어야 했다. blocker 1건
   (게이트가 TLS 검증을 끄고 있었다)은 잡았지만 그것도 단독이라 코디네이터가 인증서를
   직접 조회해 재확인해야 했다.

   문헌 근거도 같은 방향이다 — Claude 가 쓴 코드를 Codex 가 리뷰한 조건이 순효과

   −8.6pp 방향에 **거르는 층이 없다.**

   ⇒ 권고: **워커 라운드는 싼 쪽으로(작은 diff), 합본만 무편향·병합 자리를 올려라.**

```bash
orca orchestration task-list --json      # 전부 completed 인가 (provenance)

```

### ⭐ 회수 전에 **미커밋을 먼저 거둬라** (2026-09-15 실측 · 3/3)

`worker-release` 는 **터미널만** 회수하고 워크트리는 남긴다. 그런데 워커들의 워크트리에는
거의 항상 **미커밋 변경**이 있고, 그것이 전부 **리뷰 원장과 종료 보고**다.

실측(2026-09-15): 워커 셋 모두 `.claude/go-report.md` · `docs/리뷰-이력/{2026-09.md,
findings.jsonl,rounds.jsonl}` 가 미커밋이었다. 그대로 정리했으면 **리뷰 이력 41건과
종료 보고 569줄이 사라졌을 것이다.**

### ⛔⛔ 그리고 **보고가 진짜인지 재라** — 있다고 다 보고가 아니다 (2026-09-15 실측)

W2 에서 다섯 중 **셋**이 이번 차수 보고를 남기지 않았다. 그런데 파일은 다섯 다 있었다.
앞 차수 보고를 상속한 것이라 크기도 크고 시각도 그럴듯했다. 두 장은 **바이트까지 같았다.**

⇒ 판정 한 줄은 이것이다: **「보고를 썼다」 = base 의 그 파일과 blob 해시가 다르다.**
존재·크기·수정시각은 셋 다 상속본을 구분하지 못한다.

```bash
# PR 에 실렸나 — 「안 썼다」와 「커밋 안 했다」를 함께 잡는다
bash scripts/worker-report-check.sh --repo <owner/repo> --pr 195 196 197 198 199

# 워크트리에 남아 있나 — 「썼는데 커밋 안 해 곧 사라질 것」을 잡는다
bash scripts/worker-report-check.sh --base <base ref> --marker <차수 날짜> <워크트리…>
```

판정 **0** 전부 남겼다 · **1** 빠졌거나 상속본이다 · **2** 검사 자체가 안 됐다.
대조군 17검사: `bash scripts/worker-report-check.test.sh`

⚠⚠ **이 검사기 자신이 만들다가 한 번 fail-open 이었다.** 전용 보고 경로를 접두로만 맞춰서
디렉토리에 남아 있던 **남의 보고**를 자기 것으로 세고 다섯 워커를 전부 초록으로 통과시켰다.
대조군 t7 이 그 조건을 잠근다. ⇒ **탐지기를 만들 때 「무엇을 못 보나」를 픽스처로 적어라.**

⚠ 이 검사는 **코디네이터가** 돌린다. 워커 세션에 게이트를 걸지 마라 — 같은 날 워커용으로 만든
훅이 남의 질문으로 워커를 멈춰 세웠고, 워커는 그것을 풀 수단이 없었다.

### ⭐⭐ 그 순서를 **한 명령**으로 — `wave-close.sh` (2026-09-15 신설)

아래 순서는 세 번 새어 나갔다. 절차가 없어서가 아니라 **부르는 시점이 규율이었기 때문**이다.
그래서 순서를 스크립트에 박았다. 재기만 하고, 되돌릴 수 없는 일은 `--apply` 를 줘야 한다.

```bash
bash "$GF/scripts/wave-close.sh" --run <run_id> \
     --base <base ref> --marker <차수 날짜>            # 재기만 한다(기본 dry-run)
bash "$GF/scripts/wave-close.sh" --run <run_id> \
     --base <base ref> --marker <차수 날짜> --apply    # 통과하면 cleanup.sh 로 넘긴다
```

다섯을 차례로 재고 **첫 실패에서 멈춘다**: ①아직 도는 워커 ②종료 보고의 진위 ③미커밋
④리뷰 원장 무결성 ⑤파일 집합 교차. 판정 **0** 마감 가능 · **1** 막힌 것이 있다 ·
**2** 검사 자체가 안 됐다.

| 이 검사가 자동으로 하는 것 | 여전히 사람이 하는 것 |
|---|---|
| **재는 것 전부** — 워커 상태 · 보고 진위 · 미커밋 · 원장 · 교차 | **되돌릴 수 없는 것** — PR 머지 · 그림자·라이브 배포 · 합본 리뷰 must_fix 반영 |

⚠ **이 경계를 옮기지 마라.** 재는 것을 사람에게 맡기면 놓치고(오늘 5중 3을 놓칠 뻔했다),
되돌릴 수 없는 것을 자동으로 하면 되돌릴 방법이 없다.

⭐ **교차 검사는 두 부류로 가른다** — 리뷰 원장·종료 보고·게이트 파일은 워커 전원이 건드리는
것이 정상이라 「합치는 대상」이고, 소스 파일 교차만 막는다. 섞어 세면 언제나 붉어지고,
언제나 붉은 검사는 아무도 안 본다.
⚠ `failed` 로 끝난 워커는 **끝난 것으로 센다**(막지 않고 말한다). 진행 중과 섞으면 실패한
워커 하나 때문에 파도를 영영 못 닫는다.

### ⭐⭐ 그리고 **안 치우고 끝내는 것**을 훅이 막는다 — `wave-close-gate.sh`

2026-09-13 에 워커 13명이 전부 끝난 뒤에도 터미널 **15개**·워크트리 **13개**가 밤새 살아
있었다. 규약도 도구도 있었고 **부르지 않았을 뿐**이다.

이 Stop 훅은 「할 일이 남았다」가 아니라 **「자원이 살아 있다」**를 센다 — 계획 체크박스와
독립이다(계획을 다 닫아도 워크트리는 남는다). 판정은 둘의 AND 다: 이 run 에 **아직 도는
워커가 없고**, **회수되지 않은 자원이 있다**.

```bash
bash "$GF/hooks/wave-close-gate.test.sh"   # 대조군 31검사
```

⭐⭐ **이 세션이 관여한 run 만 막는다**(2026-09-16). 훅을 점검하던 세션이 지난 사흘의 파도 세
차수(잔여 컨텍스트 11개)로 매 턴 막혔고, 그 세션은 그 run 을 띄운 적이 없었다. 판별은
transcript 의 **도구 호출 입력과 도구 결과**다 — 코디네이터는 run_id 를 `--run …` 이나
`worker-list` 출력으로 반드시 만나고, 인계로 이어받은 세션도 `worker-list` 를 한 번 부르면
그때부터 막힌다. ⚠ 모델이 **산문에 인용한** run_id 는 세지 않는다(한 번 막힌 세션이 그것을
답변에 적으면 자기 출력이 자기 근거가 된다 · 대조군 t18-b). ⚠ transcript 를 못 읽으면
**종전대로 전부 본다**.

⚠⚠ **코디네이터가 닫을 수 없는 자원은 미회수로 세지 않는다.** `worker-release --help` 의 Notes 가
그 목록을 말한다 — 재사용·기존 터미널(`external_terminal`) · 사람이 인수한 터미널
(`user_takeover`) · 증명되지 않은 신원(`identity_unproven`). 그 셋만 면제하고 **넓히지 않는다**:
여기 없는 사유는 닫을 수 있다는 뜻이고, 모르는 사유를 면제하면 게이트가 조용히 꺼진다.

⚠ 등록은 **플러그인이 알아서 한다**(`hooks/hooks.json`). 레포에 사본을 두면 정본이 둘이 되고
**그 사본이 워커 워크트리로 퍼진다** — 2026-09-15 에 그 경로로 워커가 남의 질문 때문에 멈췄다.
⛔⛔ 그래서 이 훅도 **워커 세션에서는 아예 돌지 않는다**(터미널 핸들로 판별 · 대조군 t4·t5).

⇒ **회수 순서는 이렇다**(위 스크립트가 ①~⑤를 대신 재 준다):

```bash

bash scripts/worker-report-check.sh --base <base ref> --marker <날짜> <워크트리…>

# 1. 미커밋 확인 — 비어 있을 것이라고 가정하지 마라

# 2. 종료 보고를 코디네이터 쪽으로 복사(워크트리가 사라지면 같이 사라진다)
#    ⚠ 0번이 「상속본」이라 했으면 복사하지 마라 — 그 워커의 worker_done 메시지가 정본이다:
#      orca orchestration inbox --limit 200 --json
```

|---|---|---|---|
| 워커 워크트리 | Orca 가 만든 것 · `worker-list` 가 안다 | 스크립트 | `cleanup.sh --run <id> --apply` |

이 파도가 만든 것이 아니기 때문이다.
⛔ 대조군 고아에 **미커밋이 있으면 지우지 않는다.** 실측으로 그런 것이 하나 있었고(미커밋 24건)
사람이 디버깅하다 둔 것이었다. 지우는 것은 되돌릴 수 없다.

⭐ **「기억」은 새로 만들지 않았다.** `orca orchestration worker-list --run <id> --json` 이
`runId → worktreeId(전체 경로)` 를 이미 들고 있고 그것이 정본이다. `parentWorktreeId` 는
실측상 전부 비어 있어 계보로는 못 찾는다 — worker-list 가 유일한 근거다.

⭐ **본체는 삭제가 아니라 회수다.** 실측으로 정리 대기 워크트리 5개의 미커밋 변경이 **전부**
`docs/리뷰-이력/*`·`.claude/go-report.md`·`.claude/state/` 였다 — 코드가 아니라 눈에 안 띄고,
그냥 지우면 측정 이력과 provenance 를 잃는다. 그래서 삭제 전에
`~/orca/fanout-archive/<run_id>/<워크트리>/` 에 **meta·git-status·uncommitted.diff·그 파일들**을
남기고, 아카이브가 실제로 생긴 것을 확인한 뒤에만 지운다.

**판정 4종** — 하나라도 걸리면 `hold` 로 남기고 사유를 적는다. 자동으로 열지 않는다:

| 판정 | 근거 | 왜 |
|---|---|---|
| 워커가 settled 인가 | `workerState ∈ {succeeded, failed}` | 사용자 지시: **돌아가는 것은 건드리지 마라** |
| PR 이 MERGED 인가 | `gh pr list --head <branch>` | ⚠ `git rev-list origin/main..` 로 하지 마라 — squash merge 라 머지된 브랜치에도 커밋 2~11건이 남아 있다(실측) |
| 미커밋 **코드** 가 0 인가 | `status --porcelain -uall` 에서 회수 화이트리스트 밖 파일 | 사람이 봐야 하는 것 |
| gh 가 있나 | 없으면 hold | 「모르는 것을 근거로 게이트를 열지 마라」 |

**브랜치는 남긴다**(사용자 결정 2026-09-07). `orca worktree rm` 은 체크아웃된 로컬 브랜치를
함께 지우려 하므로, 스크립트가 먼저 `checkout --detach` 해서 지울 브랜치가 없게 만들고, 삭제
후 `show-ref` 로 브랜치가 남았는지 확인한다(사라졌으면 exit 1). 같은 경로에 dispatch 가 둘
이면(후속 재판정 워커 — 실측 `sec-image-scan-gate`) 한 번만 지우고 나머지는 release 만 한다.

**실물 Orca 에서만 드러난 것 2종**(2026-09-07 첫 `--apply` — 스텁 테스트는 초록이었는데 실물은 5/5 거부):
- `orca worktree rm` 은 **미커밋 파일이 하나라도 있으면 거부한다**(`Failed to delete worktree … ?? .claude/go-report.md`).
  우리 화이트리스트를 Orca 는 모른다. ⇒ 아카이브 확인 **뒤에** 회수 파일을 `checkout -- .`·`clean -fd -- <경로>` 로

  코디네이터 소유가 아니라 「사람이 띄운 외부 터미널」로 등록돼 있다. 삭제와 무관하고, rm 이 되면 사이드바에서 같이 사라진다.
- rm 이 실패하면 detach 만 남아 사이드바가 `Detached HEAD` 로 바뀐다 ⇒ 실패 경로에서 **브랜치를 다시 붙인다**.

검증: `bash "$GF/scripts/cleanup.test.sh"` (27검사 · 대조군 4종 — 게이트를 풀면
ready 로 바뀌는가 · 스텁 rm 이 미커밋을 정말 거부하는가 · detach 를 빼면 브랜치가 실제로 사라지는가 ·
두 번째 apply 는 gone 인가). ⚠ 스텁은 실물의 근사다 — 실물에서 새 거부 사유가 나오면 **스텁에 먼저 넣어라.**
⚠ 첫 실측이 결함을 하나 잡았다 — `--porcelain` 이 완전 untracked 디렉토리를 `?? .claude/`
로 뭉쳐 내서 화이트리스트가 안 걸렸다(`-uall` 로 고침). 실 레포는 `.claude/` 가 tracked 라
우연히 통과하던 것이라, **테스트 레포가 실 레포보다 엄격했던 덕에** 잡혔다.

  - **워커 질문과 내 답** — ⑦절에. 계획 밖 질문에 코디네이터가 대신 정한 것이 여기 남지
    않으면 사용자의 검증층이 사라진다

## ⛔⛔ 워커도 **같은 계정 한도를 쓴다** — 죽는다 (2026-09-15 저녁 실측)

앞 판의 이 스킬은 「워커는 독립 Orca 세션이라 코디네이터가 바뀌어도 죽지 않는다」고 적었다.
**부정확하다.** 프로세스는 살아 있지만 워커도 같은 계정으로 뜬 Claude Code 세션이라 **사용량
한도를 공유한다.** 실측으로 워커 넷이 124k 에서 150k 토큰을 쌓은 뒤 하나가 `API Error:
Connection lost` 로 끝났고, 그때 **커밋되지 않은 파일 열여섯 개**가 워크트리에 남았다.

### 죽은 워커를 되살리는 법 — 순서가 있다

⭐ 1단계에 닿기 전에 대개 **Stop 훅이 먼저 말한다.** `coordinator-inbox-gate.sh` 가 30분 넘게
heartbeat 이 없는 워커를 매 턴 알린다(차단 아님 · `CLAUDE_WORKER_HB_GAP_MIN`). 실측 분포는
표본 395건에 중앙 3.7분·p95 26분이라 30분은 넉넉한 선이다.
⚠ 그 알림은 「죽었다」가 아니다 — `ask` 나 `check --wait` 로 막힌 워커는 heartbeat 을 건너뛴다
(Orca 계약). 그래서 알림이 뜨면 아래 1단계로 **확인**하는 것이지 바로 되살리는 것이 아니다.

1. **상태는 `worker-list` 가 아니라 터미널로 확인해라.** 실측으로 목록은 여섯 다
   `ready/working` 이라 했는데 터미널은 둘이 `done` 이었다.
   ```bash
   orca terminal read --terminal <handle> --screen | tail -20
   ```
2. **커밋이 먼저다.** 워크트리는 사라지지 않지만 다음 사고에 또 잃는다. 코디네이터가 게이트를
   돌려 지금 상태를 재고, 붉어도 **무엇이 붉은지를 커밋 메시지에 적어** 커밋해라.
   ⚠ 붉은 채로 커밋하는 것이 잃는 것보다 낫다. 거짓 초록으로 적지만 마라.
3. **같은 터미널을 깨워 본다.** 그 문맥이 살아 있으면 가장 싸다.
   ```bash
   bash "$GF/scripts/coordinator-send.sh" --to terminal:<handle> --nudge-only
   ```
   ⭐ 터미널에 글자를 넣는 자리는 **래퍼 하나**다(2026-09-16). 코디네이터가 여러 자리에서
   각자 `terminal send` 를 부르면 문구도 절차도 갈라지고, 무엇을 보냈는지 아무 데도 안 남는다.
4. **안 살아나면 새 워커를 같은 워크트리에 띄운다.**
   ```bash
   orca orchestration worker-start --run <run_id> --spec "$(cat <새 지시서>)" \
     --worktree "path:/절대/경로/그-워크트리" --agent claude --json
   ```
   ⭐ 기존 워크트리는 setup 을 다시 돌리지 않고 새 터미널만 붙는다.
   ⛔ **새 워크트리를 만들지 마라.** 그러면 미커밋 작업과 무관한 자리에서 시작한다.

### 새 지시서에 반드시 넣을 셋

문맥은 새로 시작하므로 **앞 워커가 알던 것이 전부 사라진다.** 셋을 다시 넣어라.

| # | 무엇 | 안 넣으면 |
|---|---|---|
| ① | **이미 만들어진 것 목록**(커밋 해시와 파일 표) | 같은 것을 다시 만든다 |
| ② | **코디네이터가 앞 워커에게 답해 둔 결정** | 그 결정을 모른 채 다르게 간다 |
| ③ | **지금 게이트가 무엇이 붉은지**(잰 값으로) | 붉은 것을 자기가 만든 줄 알고 엉뚱한 곳을 판다 |

⚠ ③을 「게이트를 돌려 봐라」로 대신하지 마라. 워커가 처음 10분을 그것에 쓴다.

## ⛔⛔ 파일 집합을 나눠도 **장부는 겹친다** — 배치를 바꿔라 (2026-09-16 실측)

W2 에서 PR 여덟을 받는데 다섯이 충돌했다. 원인을 재 보니 **작업 분할 문제가 아니었다.**

| 충돌한 파일 | 왜 |
|---|---|
| `docs/리뷰-이력/{rounds,findings,tester}.jsonl` | 워커 **전원이 설계상 append 한다** |
| `docs/리뷰-이력/<월>.md` | 같음 |
| `.claude/go-report.md` | 공용 보고 파일(2026-09-15 폐기) |
| `.claude/tester/config.json` | **코디네이터 구성인데 워커가 고쳤다** |

⭐ 반대로 **소스는 안 겹쳤다.** 워커 둘이 함께 고친 `web/src/api/{client,types}.ts` 는 한쪽이
알림 타입에 필드를 더하고 다른 쪽이 트레이스 타입을 지워 **자동 병합됐다.** 파일 집합 교차가
곧 충돌이 아니라는 것을 그것이 보인다.

⚠⚠ **앞의 넷은 일을 아무리 잘 나눠도 겹친다.** 모든 워커가 자기 라운드와 호출을 거기 적는
것이 그 파일의 **목적**이기 때문이다. 「겹치지 않게 대상을 나눠라」로는 못 푼다.
⚠ 그리고 이 저장소는 이 부류를 **이미 여러 번** 밟았다(`git log --merges` 에 「리뷰 이력
충돌은 양쪽 라운드를 모두 남긴다」가 두 번 있다). 매번 손으로 풀었고 매번 다시 났다.

### 고치는 방향 — 공유 장부를 **워커마다 자기 파일**로

종료 보고에 이미 한 것과 같은 수술이다(`워커보고-<날짜>/<워커>.md`). 남은 넷도 같게 한다.

```
docs/리뷰-이력/rounds.jsonl      →  docs/리뷰-이력/rounds/<워커>.jsonl
docs/리뷰-이력/findings.jsonl    →  docs/리뷰-이력/findings/<워커>.jsonl
docs/리뷰-이력/tester.jsonl      →  docs/리뷰-이력/tester/<워커>.jsonl
docs/리뷰-이력/<월>.md           →  docs/리뷰-이력/<월>/<워커>.md
```

그러면 **충돌이 구조적으로 불가능하다** — 두 워커가 같은 파일을 쓰지 않는다. 읽는 쪽은
글롭으로 모으면 되고, 합치기는 이어 붙이기가 된다(키 중복 제거도 그대로 쓴다).

⚠ 이 전환은 그 원장을 **읽는 도구**(`review-ledger-check.sh`·`measure.sh`·`history.sh`)를
함께 고쳐야 한다. 한쪽만 바꾸면 검사가 빈 디렉토리에서 「중복 0」을 내고, 그것은 깨끗한
것이 아니라 **못 잰 것**이다.

### 그때까지의 규약 셋

1. ⛔ **워커는 `.claude/` 아래 공유 구성을 고치지 마라.** `tester/config.json`·`settings.json`·
   `hooks/` 는 코디네이터 몫이다. 고칠 것이 보이면 **고치지 말고 물어라.**
   (W2 에서 워커 하나가 `config.json` 을 고쳐 충돌이 났다.)
2. 장부 충돌은 **합집합으로** 푼다. 한쪽을 고르면 다른 워커의 측정이 통째로 사라지고,
   그 손실은 조용하다 — 파일은 멀쩡해 보이고 줄 수만 줄어든다.
   키는 파일마다 다르다: `tester` 는 `at`+`label` · `rounds` 는 `round` · `findings` 는 `fid`.
   월별 `.md` 는 **절 단위**로 합치고 같은 제목이면 **긴 쪽**을 남긴다(축약본을 남기면 그
   라운드의 근거가 사라진다).
3. ⚠⚠ 충돌 파일 목록을 뽑을 때 **`-c core.quotePath=false`** 를 빼지 마라. 한글 경로가
   8진 이스케이프로 나와 필터가 **하나도 매치되지 않는다.** 이 저장소가 여러 번 밟았고
   W2 머지에서도 한 번 더 밟았다.

```
Agent(subagent_type: "general-purpose", model: "opus", prompt: <감사 지시서>)
```

아끼려던 것은 토큰이고 잃을 뻔한 것은 **머지 게이트의 품질**이다.

## ⭐⭐ 워커 PR 은 **코디네이터가 받아들인다** (2026-09-15 사용자 결정)

> 「다른 워크트리에서 작업한 에이전트들의 PR 을 오케스트레이터가 리뷰해서 받아들여, 그 작업
> 브랜치에 반영되게 하는 프로세스가 되어야 할 것 같다.」

### 경계 — 한 자리만 사람이다

```
워커 브랜치 ──PR──▶ 작업 브랜치(집결지)  ──PR──▶ main
                  ▲                              ▲
              코디네이터                        사람
```

**작업 브랜치로 들어오는 것은 코디네이터가 머지한다.** 그것은 되돌릴 수 있고(브랜치를 되감으면
된다), 이 저장소의 기조가 「작업 브랜치는 자유, main 은 엄격」이다. 사람은 **main 으로 가는 한
자리**에만 선다 — 거기가 되돌리기 어려운 유일한 경계다.

⚠ 종전에는 **모든 머지**가 사람이었다. 그러면 위험하지 않은 PR 까지 사람을 기다리고, 실측으로
아홉 건이 동시에 막혀 파도 마감 자체가 멈췄다. 막는 자리를 늘린다고 안전해지지 않는다 —
사람이 아홉 번 같은 판단을 반복하면 아홉 번째는 보지 않는다.

### 코디네이터가 머지 전에 재는 것 둘

워커는 이미 자기 리뷰를 한 번 돌렸다. 그러니 **워커가 볼 수 없었던 것만** 본다. 같은 것을 두 번
보는 것은 리뷰가 아니라 지연이다.

| 무엇 | 왜 코디네이터만 할 수 있나 |
|---|---|
| **교차 파일 의미 충돌** | 워커는 자기 diff 만 봤다. 둘이 같은 파일을 고쳤는지는 전부를 본 쪽만 안다 |
| **수용 기준 대비 이탈** | 워커는 자기 지시서만 받았다. 계획 전체의 수용 기준과 대조할 수 있는 것은 코디네이터다 |

```bash
# 교차 — 정규화·워크트리내 중복까지 처리한다(셸 uniq 로 세지 마라)
python3 "$GF/scripts/_crossing.py" <base ref> <워크트리…>
```

⭐ 교차가 **있다고 곧 충돌은 아니다.** 두 워커가 같은 파일의 **다른 영역**을 고쳤으면 git 이
합친다. 실측(2026-09-15): `types.ts` 를 두 워커가 건드렸지만 한쪽은 알림 타입에 필드를 더하고
다른 쪽은 트레이스 타입을 지웠다 — 자동 병합됐다. **파일 이름이 아니라 hunk 를 봐라.**

### ⚠ 머지 전 게이트를 뺐다면 그 대가를 적어 둬라

이 저장소는 **PR 에 CI 가 돌지 않는다**. 워커 각자가 돌린 게이트 말고 자동 검증은
`pre-merge-check.sh` 하나뿐이고, 그것은 **main 으로 갈 때 한 번** 돈다. 작업 브랜치 머지마다
돌리지 않기로 했다면 그 사실을 종료 보고 ⑤에 적어라 — 「안 돌렸다」와 「돌려서 통과했다」는 다르다.

| 증상 | 원인 | 대응 |

| 리뷰 이력을 합치니 줄 수가 N배 | 워커 N 명이 **같은 base** 를 물려받아, 그 시점 미커밋이던 앞선 라운드가 N번 세어졌다(실측 5줄 → **30줄**) | `round` 키로 세고 **코디네이터 워크트리에 이미 있는 것을 빼라**. 「큰 수가 나오면 단위부터 의심하라」 |
| CI 가 **워커가 안 건드린 축**에서 실패 | 대개 플레이키다. 워커는 그 축을 재현할 수도 없다 — 그 워크트리에 `node_modules` 조차 없다 | **판별은 코디네이터 몫**이다: ①같은 소스로 다른 PR 이 통과했나 ②로컬에서 전체를 돌려도 나오나. 실측으로 web 481파일 4,444테스트가 로컬 전량 통과했고 CI 한 잡만 실패했다 |
| 워커가 자기 축의 게이트를 못 돌림 | 그 워크트리에 의존 설치가 없다(`web/node_modules` 등) | 워커 스펙에 **돌려야 하는 게이트를 명시**하고, 필요하면 코디네이터가 설치 경로를 알려라. 안 돌린 것을 「통과」로 적게 하지 마라 |
| 워커 터미널이 `API Error: Connection lost` 로 끝남 | 계정 사용량 한도. 워커도 같은 한도를 쓴다 | 위 「워커도 같은 계정 한도를 쓴다」 절. **커밋이 먼저**이고 그 다음이 재기동이다 |
| 종료 보고가 **앞 차수 내용**이다 | `.claude/go-report.md` 가 공용 파일이라 상속됐다 | `worker-report-check.sh` 로 재라. 전용 파일 규약(§4)으로 옮기면 구조적으로 사라진다 |
| 위임이 `rc 66` 으로 거부되고 워커 작업이 사라짐 | 자식이 미커밋 소스를 덮었다 | 도구가 이제 되돌린다(2026-09-15). 그래도 **구현을 커밋한 뒤에** 위임해라 |
| 웹 슬라이스 위임이 늘 `rc 67`(대조군 0건) | 격리 워크트리에 `node_modules` 가 없어 깨끗한 상태의 게이트부터 실패했다 | 고쳤다(`controlgroup.sh` 가 심링크로 잇는다). 재발하면 `gate_rc_clean` 을 먼저 봐라 |

## 대조군 — 이 스킬이 실제로 도는지 재는 법

「fan-out 했다」는 주장은 아래 셋으로 증명된다. 하나라도 없으면 그렇게 말하지 마라.

1. `orca orchestration task-list --json` 에 워커 수만큼 행이 있고 `completed` 다.
2. 워커별 워크트리에 `.claude/review/runs/<타임스탬프>/` 가 있다(리뷰가 실제로 돌았다).
3. 워커별 `.claude/go-report.md` 가 있고 7절이 채워져 있다.
4. (정리까지 했다면) `orca worktree list --json` 에 그 라운드의 워커 워크트리가 **없고**,
   `~/orca/fanout-archive/<run_id>/` 에 워커 수만큼 디렉토리가 있고, 브랜치는 `git branch` 에
   **남아 있다**. ⚠ ②③은 워크트리 안에 있으므로 정리 **전에** 확인해야 한다.
