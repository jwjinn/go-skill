# 리뷰어 회귀 평가

**정답을 아는 diff** 로 리뷰어를 채점한다.

## 왜 필요한가

`verdict.sh` 가 주는 것은 **정밀도** 하나다 — 올린 것 중 진짜가 몇 건인가.
반대쪽은 원리적으로 알 수 없다:

> **있었는데 놓친 결함이 몇 건인가**(재현율)

답을 미리 아는 코드가 있어야만 잰다. 그리고 그것이 있어야
**「프롬프트를 고쳤더니 좋아졌다」가 의견이 아니라 숫자**가 된다.

⚠ 이것은 `go test` 가 아니다. 리뷰어는 **확률적**이라 같은 입력에 다른 답을 낸다 —
통과/실패가 아니라 **비율**을 보고 **이전 기준선과 비교**하라. 그래서 test 가 아니라 eval 이다.

## ⭐ 대조군이 이 도구의 절반이다

케이스의 3분의 1 가까이가 `defect: false` — **결함이 없는 diff** 이고 정답은 「보고하지 않는 것」이다.

없으면 **「전부 결함이라고 답하는」 리뷰어가 재현율 100% 로 만점**을 받는다.
`eval.test.sh` 의 t3·t8 이 정확히 그것을 잡는다(t8 은 대조군을 빼면 무엇이 보이지 않게 되는지를
사보타주로 보여준다).

대조군은 **그럴듯하게 의심스러워야** 값을 한다 — 명백히 안전한 코드는 아무것도 시험하지 않는다.
그래서 여기 대조군은 전부 「결함처럼 보이지만 근거가 적혀 있는」 코드다
(의도된 fail-open · 정당한 `insecureSkipVerify` · 프로토콜 규약의 PUT · 정직 공백).

## 쓰기

```bash
eval.sh list                                  # 케이스 목록
eval.sh show phantom-symbol                   # 한 케이스를 정답까지(사람용)

# codex — 셸에서 돌릴 수 있는 유일한 리뷰어
eval.sh codex cases/universal.jsonl runs/cx-1
eval.sh score cases/universal.jsonl runs/cx-1 codex

# Claude 리뷰어 — 서브에이전트는 모델이 부른다
eval.sh prepare cases/universal.jsonl runs/blind-1
#   → 모델이 각 <id>.prompt.txt 로 리뷰어를 돌리고 <id>.json 으로 저장
eval.sh score cases/universal.jsonl runs/blind-1 claude-blind

# 기준선으로 남긴다(docs/리뷰-이력/eval.jsonl 에 한 줄)
eval.sh score cases/universal.jsonl runs/cx-1 codex --record "지시문 v2"
```

⭐ `--record` 는 `cases_sha` 를 함께 남긴다. **케이스가 바뀌면 점수는 비교 대상이 아니다** —
다른 시험지이기 때문이고, 그 사실을 사람이 기억하는 대신 해시가 말한다.

## 첫 기준선 (2026-09-02 · 지시문 미조정 · 같은 17건)

| 리뷰어 | 받은 것 | 위치 재현율 | 오탐률 | 거짓 주장 반박 |
|---|---|---|---|---|
| `claude-blind` | diff 만 | **12/12 = 100%** | **0/5 = 0%** | — (브리핑을 안 받는다) |
| `claude-contract` | diff + 브리핑 | **12/12 = 100%** | 2/5 = 40% ⚠ | **11/12 = 92%** |
| `codex` | diff + 브리핑 | 11/12 = 92% | 3/5 = **60%** | (측정 안 함) |

⭐ **결함 찾기에서 두 Claude 리뷰어는 구분되지 않았다**(둘 다 12/12). 이 시험지가 가르는 것은
그 축이 아니다. **contract 만 할 수 있는 것은 주장 검증**이다 — blind 는 브리핑을 못 받으므로
그 축의 능력이 **구조적으로 0**이고, 그것이 두 리뷰어를 나누는 유일한 실측 근거다.

⚠⚠ **contract 의 「오탐 2건」은 열어 보니 둘 다 진짜였다 — 대조군이 안 깨끗했다.**
- `ctl-sum-by-is-correct` — 「표식이 한 단계뿐이라 다른 환경에서는 영구 빈 결과가 된다」.
  맞다. 이 케이스는 원 레포의 실제 수정을 본떠 썼는데 **원 레포 자신이 하루 뒤 그것을
  불충분하다고 판단해 표식을 두 단계로 바꿨다.** 내가 「정상」이라 부른 코드가 이미 폐기된 판이었다.
- `ctl-phantom-looks-missing` — 「동적 조립이라 팬텀 게이트가 못 잡고 잠금이 없다」. 맞다.

즉 **40% 는 contract 의 소음이 아니라 내 케이스의 결함**이다. 지금 이 시험지는 blind 와
contract 를 오탐 축에서 **가르지 못한다**. 가르려면 대조군을 진짜로 깨끗하게 만들어야 한다.

⭐ codex 의 60% 는 성격이 다르다 — 그중에는 원 레포의 규약(근거가 적힌 fail-open 은 의도다 ·
프로토콜 PUT 은 예외다)을 몰라서 올린 것이 섞여 있다. 그것이 **「Codex 단독 발견을 must_fix 로
직행시키지 마라」의 근거**이고, 동시에 **codex 를 두는 이유**이기도 하다 — 규약을 공유하지
않는 눈이라 우리가 규약 때문에 못 보는 것을 볼 가능성이 가장 크다.

⚠⚠ **그런데 100% 는 「리뷰어가 완벽하다」가 아니다. 시험지의 천장이다.**
원 레포의 「모든 입력에 같은 답이 나오면 그 답은 근거가 아니다」가 여기 적용된다.
만점이 나온 이유로 최소 셋을 배제하지 못했다:

1. **케이스를 쓴 것과 푸는 것이 같은 모델 계열이다.** 내가 심을 생각을 한 결함을
   같은 계열이 찾는 것은 놀랍지 않다 — **공유된 사전 지식**이 그대로 점수가 된다.
   codex 가 같은 시험지에서 다른 점수를 낸 것이 그 편향의 크기를 보여준다.
2. **케이스가 부류의 「깨끗한 표본」이다.** 실제 결함은 문맥에 묻혀 있고 여러 정상 변경과 섞여 온다.
   여기서는 한 diff 에 한 결함이고 주변이 조용하다.
3. **12건은 천장에 쉽게 닿는 크기다.** 한 건이 곧 8%p 라 분해능이 없다.

**그래서 이 표를 이렇게 읽어라** — 절대 수치는 「이 17종을 잡는다」까지이고,
**리뷰어끼리의 비교**와 **같은 리뷰어의 시간에 따른 변화**에만 근거로 써라.
천장을 올리려면 케이스를 **어렵게** 만들어야 한다: 한 diff 에 정상 변경 여럿 + 결함 하나,
그리고 **리뷰어와 다른 계열이 쓴 케이스**(또는 실제 사건에서 그대로 역산한 diff).

## 읽는 법

- **위치 재현율** — 결함 파일(과 줄)을 짚었나. 자동 채점에서 **가장 믿을 만한 신호**다.
- **사유까지 / 위치만** — 키워드 매칭이라 약한 신호다. 그래서 따로 센다 —
  합치면 **옳은 줄을 엉뚱한 이유로 지적한 것**이 만점으로 묻힌다.
- **오탐률** — 대조군에서 보고한 비율. 재현율만큼 중요하다.
- **미측정** — 리뷰어 산출이 없다. **놓침이 아니라 도달 실패**이고 분모에서 빠진다
  (원 레포가 반복해서 배운 「0이 나오면 탐지기부터 의심하라」).
- **부류별** — 약한 부류가 곧 **프롬프트를 고칠 자리**다.

## 케이스 추가

`cases/<이름>.jsonl` 한 줄이 한 케이스다. 형식은 [case-schema.json](case-schema.json).

```json
{"id":"...", "class":"...", "lang":"go", "defect":true,
 "why":"왜 결함인가(사람용 — 리뷰어에게 안 나간다)",
 "origin":"진행로그 2026-08-12",
 "diff":"--- a/x.go\n+++ b/x.go\n@@ ...",
 "expect":{"file":"x.go","line":12,"any_of":["키워드"],"min_severity":"major"}}
```

⭐ **결함 케이스를 넣으면 대조군도 같이 넣어라.** 그 부류와 **닮았지만 정상인** 코드가 좋다.

⚠⚠ **오픈북에 주의하라.** `why`·`expect`·`class` 는 프롬프트로 나가지 않는다
(`_prepare.py` 의 화이트리스트가 그 경계이고 `eval.test.sh` t10 이 잠근다).
그런데 **리뷰어에게 주는 프로젝트 규칙 파일**(`.claude/review-rules.md`)은 다르다 —
그 함정 목록이 케이스와 같은 출처에서 왔다면 답을 참고서로 준 셈이다.
비교는 **규칙 파일을 준 조건과 안 준 조건**으로 나눠서 해라. 그러면 오히려
「그 함정 목록이 값을 하는가」를 재게 된다.

⚠ diff 안에 **판단 재료가 다 있어야** 한다. 케이스의 파일은 실재하지 않으므로 리뷰어가
열어 볼 수 없다. 문맥을 넉넉히 넣어라.

## ⚠ 2026-09-02 — 케이스의 도메인 어휘를 중립화했다

공개 배포를 위해 17건의 **경로·심볼·산문에서 원 레포 제품의 기능·구조를 추정할 수 있는
어휘를 걷어냈다**(예: 특정 서빙 백엔드 지표명 → 일반 워커 지표명, 제품 슬라이스 이름 →
중립 이름). **결함 구조와 줄 번호는 건드리지 않았다** — `expect.file`/`expect.line` 정합성을
스크립트로 확인했다(17/17).

⚠ **그래서 아래 기준선 수치는 이전 문안에서 잰 값이다.** 문안이 바뀌면 리뷰어가 읽는
프롬프트도 바뀌므로, 엄밀히 비교하려면 **다시 한 번 돌려 기준선을 갱신**해야 한다.
바뀌지 않았을 가능성이 높지만(결함은 그대로다) 그것은 가정이고 측정이 아니다.

## 케이스 두 벌

| 파일 | 무엇 | 어디에 |
|---|---|---|
| `cases/universal.jsonl` | 어느 프로젝트에나 있는 부류 | 플러그인에 실린다 |
| `cases/<프로젝트>.jsonl` | 그 프로젝트의 불변식·스택을 알아야 잡히는 것 | **그 프로젝트에만** |

⚠ 특화 케이스를 플러그인에 싣지 마라 — 다른 프로젝트에서는 **오답**이 된다
(예: "PUT 을 쓰지 마라"는 어떤 프로젝트의 심사 규약이지 보편 규칙이 아니다).

## ⚠ 한계 — 이 숫자로 말할 수 없는 것

**이 평가가 답하지 못하는 질문을 먼저 알아라.** 안 그러면 「재현율 75%」가 실제보다
많은 것을 뜻한다고 믿게 된다.

1. **집합에 없는 부류는 못 잰다.** 케이스는 사람이 쓴 것이라 **쓴 사람이 아는 결함만** 담긴다.
   리뷰어가 이 25건을 다 잡아도 그것은 「이 25종을 잡는다」이지 「좋은 리뷰어다」가 아니다.
   ⭐ 그래서 **놓쳐서 아팠던 것을 계속 케이스로 추가**하는 것이 이 도구의 본체다.
2. **사유 채점은 내 표현에 편향된다.** `any_of` 는 내가 예상한 단어이고, 리뷰어가 옳은 판단을
   다른 말로 쓰면 「위치만」이 된다. 그래서 **위치 재현율에는 「위치만」도 적중으로 넣는다** —
   두 수치를 나란히 보고, 「위치만」이 많으면 채점 키워드를 의심해라(리뷰어가 아니라).
3. **diff 만 보는 조건이다.** 실사용 리뷰어는 파일을 열어 주변 코드를 읽는다. 여기서는 못 하므로
   **문맥이 필요한 결함은 실제보다 어렵게** 나온다. 실사용 성능의 하한으로 읽어라.
4. **한 번 돌린 값은 근거가 아니다.** 확률적이라 같은 케이스에 다른 답이 나온다.
   같은 조건을 최소 3회 돌려 평균과 편차를 보고, 비교는 **기준선 대비**로 해라.
