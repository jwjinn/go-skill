# /go:start — 승인하고 실행한다

사용자가 이 명령을 친 것이 **승인**이다. 이 명령은 Claude 가 스스로 부를 수 없다(`disable-model-invocation`).

## 0. 무엇을 실행하나

`$ARGUMENTS` 에서 `--merge`(검사 통과 시 머지까지)를 떼어 기억하고, 나머지를 본다:

- 초안 디렉토리 이름이 있으면 그 디렉토리.
- 없으면 `.claude/plans/*/` 에서 고른다:
  - 미완료 체크박스가 남은 `plan.md` 가 있으면 → **이미 승인된 계획을 이어간다**(2단계부터 · 닫힌 항목은 건너뛴다).
  - 없고 `plan.md` 없는 `draft.md` 가 하나면 → 그것을 확정한다(1단계).
  - 후보가 여럿이면 디렉토리 이름과 원 요청 한 줄씩 보여 주고 묻는다. 없으면 「먼저 `/go:plan <요청>` 으로 계획을
    만들어 주세요」 한 줄로 끝낸다.

## 1. 확정 — `draft.md` → `plan.md`

- 「결정 필요」 절에 답이 없는 항목이 남았으면 확정하지 말고 그 항목을 묻는다(`AskUserQuestion`, 없으면 출력하고 끝).
  고르지 않은 목업(`[목업]` 줄)도 열린 항목이다. 고르기 전에는 화면을 구현하지 않는다.
- 초안 내용을 `Write` 로 같은 디렉토리의 **`plan.md`** 에 쓴다. **이 순간부터** plan-gate 가 미완료 체크박스를 지킨다 —
  다 끝내기 전에 턴을 끝내려 하면 막힌다. 그것이 의도다.
- 「실측」 절의 파일:줄 이 아직 맞는지 한 번 확인한다(초안을 쓴 뒤 코드가 바뀌었을 수 있다). 어긋나면 고쳐서 확정한다.

## 2. 구현

- 배치가 하나면 단계를 순서대로 한다. 끝낸 항목은 `plan.md` 에서 `- [x]` 로 닫는다. 단계 경계에서 「이어할까요?」를 묻지 마라.
- 단계에 `명세: <목업 경로>` 가 붙어 있으면 그 목업을 먼저 열고 **그대로** 구현한다. 목업에 없는 것을 더하거나 있는 것을
  빼야 하면 보고 4절에 사유를 적는다. 저장소의 목업 규약에 구현 대조 검사가 있으면 그 단계의 검증으로 돌린다.
- **배치가 둘 이상이면 병렬로 띄운다** — `Agent` 도구를 배치마다 하나씩, **같은 응답 안에서** 전부 호출한다
  (`isolation: "worktree"` · `subagent_type: "general-purpose"`). 띄우기 전에 파일 집합 교집합이 비었는지 한 번 더 센다.
  `<시작 커밋>` 은 띄우기 직전 `git rev-parse HEAD`. 목업 경로는 절대 경로로 준다(워커의 워크트리에는 커밋하지 않은
  목업 파일이 없다). 워커 프롬프트에는 이것을 그대로 넣는다:
  > 너는 병렬 워커다. 네 배치는 「<이름>」이고 할 단계는 <단계 목록 · 검증 포함>이다. **네 파일 집합은 <경로들> 뿐이다**
  > — 그 밖의 파일은 읽기만 하고 고치지 마라. 공유 자원 <목록> 은 건드리지 마라. 사람에게 물을 수 없다 — 갈림길을
  > 만나면 그 자리에서 멈추고 무엇이 막는지 보고하라. <화면 단계가 있으면: 명세 목업은 <절대 경로> 다 — 먼저 열고 그대로
  > 구현하라. 더하거나 뺀 것은 사유와 함께 보고하라.> 구현과 검증이 끝나면 네 워크트리 안에서 커밋하고(메시지는 저장소
  > 커밋 규약대로), **그다음 `Skill` 도구로 `go:review` 를 인자 `--no-pr --base <시작 커밋>` 으로 불러라** — codex 가
  > 네 변경을 리뷰하고, 너는 짚인 자리만 열어 확인한 뒤 고치고 다시 커밋한다(한 사이클 · 재리뷰 없음). **마지막 메시지에
  > 브랜치 이름 · 최종 커밋 해시 · 바꾼 파일 · 돌린 검증과 결과 · codex 발견 수와 반영·보류 · 못 한 것**을 적어라.
  워커가 돌아오면: 보고의 브랜치를 **초안에 적은 순서대로** 현재 브랜치에 머지한다(파일 집합이 겹치지 않으니 충돌이
  나면 계획이 틀린 것이다 — 멈추고 사용자에게 말한다). 머지마다 그 배치의 체크박스를 닫는다. 워커가 「막혔다」고 하면
  그 배치는 열어 두고 보고에 적는다. 끝난 워크트리는 `git worktree remove` 로 치운다(자원 회수 절).
  합친 뒤 저장소 게이트(빌드·테스트)를 한 번 돌린다 — 배치마다 초록이어도 합본이 초록인지는 다른 문제다.
- 범위에서 빼야 할 항목은 `[x]` 로 위장하지 말고 **줄을 지우고** 보고에 이유를 적는다.
- 사용자 답 없이는 진행이 무의미한 갈림길이 나오면 `AskUserQuestion` 으로 묻고 기다린다(이것이 멈춰도 되는 유일한 경우다).

## 3. 마무리 — `go:review`

구현 단계가 전부 닫히면 `Skill` 도구로 `go:review` 를 부른다(`--merge` 를 받았으면 그대로 넘긴다). 병렬이었으면 이것이
**합본 리뷰**다 — 배치 사이의 상호작용은 워커 리뷰가 못 본다. 끝나면 「리뷰·검사·PR」 항목을 닫는다.

## 4. 최종 보고 — 다섯 절, 짧게

1. 목표 계약 대비 판정(수용 기준마다 됐다/안 됐다)
2. 만든 것(파일:줄)
3. 리뷰 요지(발견 · 반영 · 보류 · 검사 · PR). 병렬이었으면 **워커별 리뷰 결과**(배치 · codex 발견 · 반영 · 보류)를 한 줄씩 넣고 합본 리뷰를 따로 적는다
4. 못 한 것과 사람이 할 것
5. 있었던 일(예상 밖의 것 · 되돌린 것 · 측정값). 「특이사항 없음」으로 채우지 마라

보고 뒤 `plan.md` 의 상자가 전부 닫혔는지 확인한다. 자원 회수 항목이 있으면 그것도 닫는다.

## 하지 마라

- 내장 `/code-review` 를 부르지 마라(리뷰는 `go:review` 안의 codex 하나 — Claude 토큰을 아끼려는 사용자 결정).
- 반영 뒤 다시 리뷰를 돌리지 마라. 한 단계에 한 사이클이다.
