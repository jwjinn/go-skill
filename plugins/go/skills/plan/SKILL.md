# /go:plan — 계획을 만들고 다듬는다

이 명령은 **읽기와 계획·목업 파일 쓰기만** 한다. 실행은 사람이 `/go:start` 를 쳐야 시작된다 — 그 명령은 Claude 가
스스로 부를 수 없게 막혀 있고, 그것이 「승인은 사람만 한다」의 구조다.

## 0. 인자

- `$ARGUMENTS` 가 요청 문장이면 그것이 **원 요청**이다. 그대로 인용해 초안 머리에 둔다(바꿔 말하지 마라).
- 기존 초안 디렉토리 이름(`20261012-xxx`)이면 그 초안을 열고 4단계부터 이어간다.
- 비어 있으면 `.claude/plans/*/` 에서 `plan.md` 없이 `draft.md` 만 있는 것(보류한 초안)을 찾는다. 하나면 그것을,
  여럿이면 디렉토리 이름과 원 요청 한 줄씩 보여 주고 묻는다. 없으면 「무엇을 만들까요」 한 줄만 묻고 끝낸다.
  다시 열 때는 「실측」 절의 파일:줄 이 아직 맞는지 먼저 확인하고, 어긋나면 고쳐서 보여 준다.

## 1. 실측 (읽기만 한다)

계획을 쓰기 전에 그 자리의 코드를 연다. CLAUDE.md 에 「증상 → 슬라이스 → 진입 파일」 표가 있으면 거기서
출발한다. 이미 있는 것(헬퍼·부품·검사기)을 먼저 찾는다 — 있는데 안 쓰는 것이 가장 흔한 낭비다.
영역이 여럿이라 한 세션이 다 읽으면 문맥이 넘칠 때만 `Explore` 에이전트에 영역별로 나눠 맡긴다(요약만 돌려받는다).
한두 파일이면 직접 읽는다. 이 단계에서 파일을 고치지 마라.

## 2. 초안을 쓴다 — `.claude/plans/<YYYYMMDD-slug>/draft.md`

`Write` 도구로 쓴다(Bash 재지향으로 쓰지 마라 — plan-gate 는 Write/Edit 흔적으로 「이 세션의 계획」을 가른다).
**초안은 `draft.md` 다.** plan-gate 는 `plan.md` 만 보므로, 초안을 고치는 동안에는 턴이 막히지 않는다.

```markdown
# <제목> — <YYYY-MM-DD>

## 목표 계약
- 원 요청: 「<$ARGUMENTS 그대로>」
- 수용 기준: <끝났다고 볼 수 있는 관찰 가능한 조건 1~3개>
- 범위 밖: <하지 않을 것 — 비워 두지 마라>

## 실측
<1단계에서 본 것. 파일:줄 로>

## 단계
- [ ] <단계> — 검증: <무엇을 돌려 확인하나>
- [ ] …
- [ ] 리뷰·검사·PR — /go:review

## 화면 (목업 대상)
<화면을 새로 만들거나 바꾸는 곳이 없으면 「없음」. 있으면 계획 전체에서 전부 뽑아 한 표로:>
캔버스 계정: <캔버스를 쓸 때만 · 2-b 3 에서 확인한 `claude auth status` 의 email>
| 화면 | 신규/수정 | 진입 경로(메뉴·URL) | 바뀌는 것 | 관련 단계 | 목업 |
|---|---|---|---|---|---|

## 병렬 배치
<배치가 하나면 「없음(순차)」. 둘 이상이면 배치마다:>
- 배치 A「<이름>」 — 단계: <위 단계 중 어느 것> · 파일 집합: <경로들> · 공유 자원: <DB·포트·픽스처 중 건드리는 것, 없으면 없음> · 완료 조건: <검증 명령>
- 배치 B「<이름>」 — …
- 합치기(/go:start 세션): <머지 순서 · 합친 뒤 돌릴 게이트>

## 결정 필요(승인 전)
- <사용자만 답할 수 있는 갈림길. 없으면 「없음」>

## 자원 회수
<임시 파일·브랜치·워크트리 중 끝나면 치울 것. 없으면 「없음」>
```

단계는 **검증을 붙여서** 쓴다. 테스트를 만들 단계에는 「보호를 깨서 붉어지는 것을 본다」를 넣는다(대조군 없는
테스트는 근거가 아니다).

**병렬 배치는 초안에서 정한다.** 서로 파일 집합이 겹치지 않고 공유 자원을 같이 건드리지 않는 단계 묶음만 배치로
나눈다. 파일 집합이 한 경로라도 겹치면 배치가 아니라 순차다 — 초안 단계에서 합쳐라. 워커는 사람에게 묻지 못하므로,
배치가 둘 이상이면 **결정 필요 절을 더 꼼꼼히** 채운다(워커가 갈림길을 만나면 멈춰 보고하는 것이 전부다).

## 2-b. 화면 목업 — 화면을 바꾸는 계획이면

화면 정의는 실행 전에 끝낸다. 계획 전체에서 화면을 새로 만들거나 바꾸는 곳을 **먼저 모두** 뽑고, 그 화면마다
**목업 4안(A~D)** 을 만들어 사용자가 피드백을 주고 하나씩 고르게 한다. 모든 화면이 골라진 뒤에만 `/go:start` 가
실행되므로, 실행 중에는 화면 때문에 멈추지 않는다. 고른 안이 그 화면의 명세다.

1. **화면을 전부 뽑는다.** 단계를 다 쓴 뒤 단계마다 「사용자가 보는 화면의 구성·배치·상호작용이 바뀌나」를 묻고,
   바뀌는 화면을 초안의 「화면」 표에 모은다(신규/수정 · 진입 경로 · 바뀌는 것 · 관련 단계). 대상이 아닌 것: 의도한
   동작으로 되돌리는 버그 수정, 화면이 그대로인 내부 수정, 사용자가 캡처 · 문구로 결과를 직접 지정한 수정(그 단계에
   `— 명세: 사용자 지시(<날짜> · 캡처/문구)` 를 붙인다). 애매하면 「결정 필요」에 「<화면> 은 목업 없이 갈까요」를
   넣는다. 사용자가 「목업 없이」라고 하면 만들지 않는다.
2. **목업 규약을 찾는다.** CLAUDE.md 와 `.claude/rules/*.md` 에서 「목업」을 검색해 가리키는 문서를 연다. 규약이
   자리·형식·디자인 시스템을 정한다.
3. **자리를 정한다.**
   - 규약이 Claude Design 디자인 시스템(Artifact 주소)을 지정했으면 → **캔버스**: 화면마다 Design 유형 캔버스 하나에
     아트보드 A~D 를 그리고, 그 디자인 시스템을 **명시해서** 설치한다(조직 기본값이 따로 있어도 규약이 지정한 것을 쓴다).
     캔버스 제목은 「<화면> 목업 4안」.
     그리기 전에 연동을 확인한다: 이 세션에 `Artifact` 도구가 있고, `Artifact` list(`type: "Design System"`)에 규약의
     주소가 보여야 한다. 로그인 계정도 본다: `claude auth status` 의 `email` 이 규약에 적힌 캔버스 소유 계정과 같아야
     하고(규약에 없으면 처음 본 email 을 기준으로 삼는다), 그 값을 초안 「화면」 절의 「캔버스 계정」에 적는다. 로그인은
     `~/.claude` 를 같이 쓰는 모든 세션에 적용되어 도중에 바뀌므로, 캔버스를 그리거나 다시 읽는 묶음마다 다시 대조한다.
     다르거나 캔버스가 「not found」면 「<캔버스 계정> 으로 `/login` 해 주세요」라고 청하고 멈춘다(다른 계정으로 만든
     캔버스는 소유 계정에서 보이지 않는다). **둘 중 하나라도 아니면 조용히 로컬 HTML 로 바꾸지 말고 멈춰서** 사용자에게 무엇이 빠졌는지와
     설정 순서를 안내한다:
     1. Claude Code 를 claude.ai 계정(조직 계정)으로 로그인한다 — `/login`.
     2. 조직 설정 Organization settings › Artifacts 에서 Artifacts · Design systems · Design 을 켠다(조직 소유자 몫).
     3. 디자인 시스템이 아직 없으면 저장소에서 `/design-login` 뒤 `/design-sync` 로 부품을 올린다.
     4. Claude 앱 Artifacts 페이지에서 Migrate team design systems 를 누른다(옛 claude.ai/design 에 있는 시스템을 옮긴다).
     5. 디자인 시스템 주소를 저장소 목업 규약에 적는다.
     그리고 묻는다: 「설정한 뒤 다시 할까요, 이번에는 로컬 HTML 로 할까요?」 사용자가 로컬을 고를 때만 아래로 간다.
   - 규약이 디자인 시스템을 정하지 않았으면 → **로컬 HTML**: 규약이 정한 폴더, 없으면
     `.claude/plans/<slug>/mockups/<화면>/` 에 `A.html`~`D.html` 과 `index.html`.
4. **기능 목록을 만든다.** 화면마다 `Agent`(general-purpose · `model: "opus"`) 하나에 맡기고, 화면이 여럿이면 같은 응답
   안에서 전부 띄운다. 이 세션의 모델이 무엇이든(Fable 이어도) 목업의 범위를 정하는 실측은 Opus 가, 그리기는 Sonnet 이
   한다(목업에 계획 세션 모델의 토큰을 쓰지 않게). 이 세션은 목록을 다시 쓰거나 보태지 않고 5단계에 그대로 넘긴다.
   프롬프트에 넣을 것:
   > 화면 「<이름>」의 목업에 들어갈 기능 목록을 코드에서 실측해 만들어라. 진입 경로: <메뉴·URL>. 이번 계획에서 바뀌는
   > 것: <단계 요지>. 먼저 <규약 문서> 를 읽고, 규약이 목업에 넣으라고 정한 것(진입 경로 · 하위 화면 · 기능 전량 · 상태 등)을
   > 빠짐없이 항목으로 적어라. 항목마다 근거 파일:줄을 붙여라. 코드와 문서를 고치지 마라. 마지막 메시지에는 그 목록만 적어라.
5. **그린다.** 화면마다 `Agent`(general-purpose · `model: "sonnet"`) 하나에 그 화면의 4단계 목록을 넘겨 맡기고, 화면이
   여럿이면 같은 응답 안에서 전부 띄운다(목업이 이 세션의 문맥을 채우지 않게). 캔버스인데 서브에이전트에 `Artifact` 도구가
   없으면 이 세션이 대신 그리지 말고 멈춰서 사용자에게 알린다.
   프롬프트에 넣을 것:
   > 화면 「<이름>」의 목업 4안(A~D)을 <캔버스 / 출력 디렉토리> 에 만들어라. 진입 경로: <메뉴·URL>. 그 화면의
   > 기능 목록: <4단계 목록 그대로>. 이번 계획에서 바뀌는 것: <단계 요지>. 먼저 <규약 문서> 와 <디자인
   > 문서> 를 읽고 따르라. 캔버스면 디자인 시스템 <주소> 를 설치하고 실제 부품을 불러 써라(비슷하게 흉내 내지 마라).
   > 네 안은 배치나 흐름의 방향이 서로 달라야 한다. 색이나 간격만 바꾼 변형은 다른 안이 아니다. 값을 지어내지 마라.
   > 마지막 메시지에 캔버스 주소(또는 파일 경로)와 안마다 한 줄 요약을 적어라. 그리고 위 기능 목록의 항목마다 그 항목을
   > 그린 아트보드(또는 파일)를 안별로 적은 표를 붙여라. 그리지 않은 항목은 칸을 비우고 사유를 적어라.

   돌려받은 표에 사유 없는 빈 칸이 있으면 같은 서브에이전트에 채우라고 다시 보낸다(`SendMessage`). 사유가 있는 빈 칸은
   「결정 필요」에 올린다. 이 세션은 표만 읽고 아트보드를 직접 열지 않는다.
6. **초안에 반영한다.** 「화면」 표의 목업 칸에 캔버스 주소(또는 `index.html` 경로)를 적고, 「결정 필요」에 화면마다:
   `- [ ] [목업] <화면> — A~D 중 · 보기: <캔버스 주소 / index.html 경로>`.
   고르면 `- [x] [목업] <화면> — 답: C (<캔버스 주소> · C.dc.html)` 로 닫고, 그 화면을 고치는 단계 끝에
   `— 명세: <캔버스 주소> · C.dc.html` 을 붙인다(로컬이면 파일 경로). 섞은 답(「C 에 D 의 묶음 제목」)은 그대로 적고 명세에
   무엇을 어디서 가져오는지 적는다.

## 3. 결정을 먼저 닫는다

「결정 필요」에 항목이 있으면 `AskUserQuestion` 으로 **한 자리에서 전부** 묻는다(도구가 없는 세션이면 질문을
번호로 출력하고 턴을 끝낸다). 답이 본문을 바꾸면 초안을 다시 쓴다.
목업 선택은 화면마다 질문 하나로 묻는다. 선택지는 A~D 이고 설명에 안마다 한 줄 요약을 넣는다(한 번에 넷까지 물을 수
있으므로, 화면이 넷을 넘으면 나눠 묻는다). 묻기 전에 캔버스 주소(또는 `index.html` 경로)를 보여 준다. 로컬 HTML 이고
macOS 면 `open` 으로 연다. 사용자가 캔버스에서 먼저 고쳐 보고 고르겠다고 하면 묻지 말고 협의 루프로 넘어간다.

## 4. 다듬는다 — 협의 루프

초안을 보여 주고 이 한 줄로 끝낸다:

> 고칠 것이 있으면 그냥 말해 주세요. 이대로 실행하려면 **`/go:start`**, 나중에 하려면 그대로 두면 됩니다(초안은 남습니다).

그 뒤 사용자의 모든 메시지는 **고치는 말**이다. 형식을 요구하지 마라:
- 「이것도 추가해」「그 화면도 같이」 → 실측을 그만큼 더 하고 단계·파일 집합·병렬 배치·수용 기준을 늘린다. 추가된 일이
  기존 배치와 파일 집합이 안 겹치면 새 배치로, 겹치면 같은 배치에 넣는다.
- 「3단계 빼」「그건 다음에」 → 줄을 지우고 「범위 밖」 절에 옮긴다.
- 「C 반영해」「댓글 반영해」 → 로그인 계정을 대조한 뒤 `Agent`(general-purpose · `model: "sonnet"`) 하나에 맡긴다.
  프롬프트에 캔버스 주소 · 아트보드 · 사용자가 한 말을 넣고 이렇게 시킨다: 그 아트보드를 다시 읽고(`Artifact` read · `path`),
  댓글도 읽어라(`ArtifactComments` read · deferred 도구라 `ToolSearch` 로 먼저 불러 온다). 사람이 직접 고친 것은 정본이다 —
  덮어쓰지 말고 그 위에 더하라. 펜으로 쓴 메모도 반영하고, 댓글이나 말로 캔버스 수정을 청했으면 그 아트보드를 고쳐 다시
  올려라. 마지막 메시지에 바뀐 점을 표로(바뀐 것 · 코드로 옮기면 할 일 · 정해야 할 것) 적어라.
  이 세션은 그 표를 보여 주고, 바뀐 점이 계획을 바꾸면(새 열 · 새 동작 · 새 화면) 단계와 수용 기준을 고친다.
- 「목업 다시」「B 에서 표만 바꿔」 → 그 화면의 목업만 2-b 5 대로(Sonnet 서브에이전트) 다시 만들고, 그 화면의 목업 결정 줄을 다시 연다.
  화면의 범위가 바뀌었으면(새 기능 · 새 하위 화면) 2-b 4 의 Opus 목록부터 다시 만든다.
  새로 화면이 추가되면 「화면」 표에 넣고 그 화면의 목업 4안도 만든다(2-b).
- 「왜 이렇게 나눴어?」 같은 질문 → 답하고, 답이 계획을 바꾸면 고친다.
- 새 요청이 원 요청과 무관하게 커지면(다른 기능·다른 화면 묶음) 「따로 `/go:plan` 으로 나눌까요, 이 계획에 넣을까요」를 묻는다.
고칠 때마다 `draft.md` 를 `Edit` 로 갱신하고, **바뀐 절만** 보여 준 뒤 현재 단계 체크리스트 전체와 위 한 줄을 다시 붙인다
(매번 전문을 다시 찍지 마라). 원 요청 줄은 바꾸지 않고, 추가된 요청은 그 아래 「추가 요청(날짜)」 줄로 쌓는다.

⛔ 사용자가 「시작」「진행해」「좋아 해줘」처럼 **말로** 실행을 청해도 구현하지 마라. 「실행은 `/go:start` 를 쳐 주세요」
한 줄로 답한다. `plan.md` 를 쓰는 것도, 코드를 고치는 것도 `/go:start` 안에서만 일어난다.

## 하지 마라

- 코드를 고치지 마라. 이 명령이 쓰는 것은 `draft.md` 와 목업(캔버스 또는 목업 파일)뿐이다.
- `plan.md` 를 쓰지 마라. 그것은 승인이고, 승인은 `/go:start` 다.
