# /go — 계획 → 승인 → 구현 → 마무리

사람은 **앞(계획 승인)과 뒤(최종 보고)**에만 있다. 중간은 plan-gate(완주)와 /review-loop(리뷰·검사·PR)이 지탱한다.
이 스킬은 코드를 쓰지 않는다 — 순서를 지키게 하는 지시문이다.

## 0. 인자

- `$ARGUMENTS` 가 있으면 그것이 **원 요청**이다. 그대로 인용해 계획 머리에 둔다(바꿔 말하지 마라).
- 비어 있으면 `.claude/plans/*/plan.md` 중 미완료 체크박스가 있는 것을 찾아 **5단계부터 이어간다.**
  없으면 「무엇을 만들까요」 한 줄만 묻고 끝낸다.

## 1. 실측 (읽기만 한다)

계획을 쓰기 전에 그 자리의 코드를 연다. CLAUDE.md 에 「증상 → 슬라이스 → 진입 파일」 표가 있으면 거기서
출발한다. 이미 있는 것(헬퍼·부품·검사기)을 먼저 찾는다 — 있는데 안 쓰는 것이 가장 흔한 낭비다.
이 단계에서 파일을 고치지 마라.

## 2. 초안을 쓴다 — `.claude/plans/<YYYYMMDD-slug>/draft.md`

`Write` 도구로 쓴다(Bash 재지향으로 쓰지 마라 — plan-gate 는 Write/Edit 흔적으로 「이 세션의 계획」을 가른다).
**초안은 `draft.md` 다.** plan-gate 는 `plan.md` 만 보므로, 초안을 고치는 동안에는 턴이 막히지 않는다.

```markdown
# <제목> — <YYYY-MM-DD>

## 목표 계약
- 원 요청: 「<$ARGUMENTS 그대로>」
- 수용 기준: <끝났다고 볼 수 있는 관찰 가능한 조건 1~3개>
- 범위 밖: <하지 않을 것 — 비워 두지 마라>

## 실측
<1단계에서 본 것. 파일:줄 로>

## 단계
- [ ] <단계> — 검증: <무엇을 돌려 확인하나>
- [ ] …
- [ ] 리뷰·검사·PR — /review-loop

## 결정 필요(승인 전)
- <사용자만 답할 수 있는 갈림길. 없으면 「없음」>

## 자원 회수
<임시 파일·브랜치·워크트리 중 끝나면 치울 것. 없으면 「없음」>
```

단계는 **검증을 붙여서** 쓴다. 테스트를 만들 단계에는 「보호를 깨서 붉어지는 것을 본다」를 넣는다(대조군 없는
테스트는 근거가 아니다). 병렬로 할 수 있는 단계는 표시한다.

## 3. 결정을 먼저 닫는다

「결정 필요」에 항목이 있으면 `AskUserQuestion` 으로 **한 자리에서 전부** 묻는다. 답이 본문을 바꾸면 초안을 다시
쓴다. 열린 결정을 두고 4단계로 가지 마라.

## 4. 승인을 받는다 — 만족할 때까지

초안 전문을 보여 주고 `AskUserQuestion` 으로 묻는다:

- **시작 (Recommended)** — 이 계획대로 구현한다
- **고친다** — 사용자가 적는 메모대로 초안을 고쳐 다시 보여 준다(몇 번이든)
- **보류** — 초안을 남겨 두고 끝낸다(draft.md 는 게이트가 보지 않으므로 아무것도 막히지 않는다)

사용자가 「머지까지」「끝까지」라고 했으면 기억해 둔다(6단계의 `--merge`).

⛔ **승인은 사람만 한다.** `AskUserQuestion` 도구가 없는 세션(헤드리스 · 도구 목록에 부재)이면 초안 전문과
「시작 · 고친다 <메모> · 보류 중 하나로 답해 달라」는 한 줄을 출력하고 **턴을 끝낸다.** 사용자의 다음 메시지가
「시작」이면 5단계, 「고친다 …」면 초안을 고쳐 다시 4단계, 「보류」면 끝이다. 결정 필요 항목이 없다는 이유로,
또는 질문 도구가 없다는 이유로 스스로 승인하지 마라(2026-10-11 E2E 에서 그렇게 건너뛴 적이 있다 — draft.md 가
게이트에 안 걸리는 이유가 바로 이 대기 때문이다).

## 5. 시작 — 계획을 확정하고 구현한다

- 초안 내용을 `Write` 로 **`plan.md`** 에 쓴다(같은 디렉토리 · 「결정 필요」절은 답으로 채운다). **이 순간부터**
  plan-gate 가 미완료 체크박스를 지킨다 — 다 끝내기 전에 턴을 끝내려 하면 막힌다. 그것이 의도다.
- 단계를 순서대로 한다. 끝낸 항목은 그 파일에서 `- [x]` 로 닫는다. 단계 경계에서 「이어할까요?」를 묻지 마라.
- 범위에서 빼야 할 항목은 `[x]` 로 위장하지 말고 **줄을 지우고** 보고에 이유를 적는다.
- 사용자 답 없이는 진행이 무의미한 갈림길이 나오면 `AskUserQuestion` 으로 묻고 기다린다(이것이 멈춰도 되는 유일한 경우다).

## 6. 마무리 — `/review-loop`

구현 단계가 전부 닫히면 `Skill` 도구로 `review-loop` 을 부른다(사용자가 머지까지 맡겼으면 인자 `--merge`).
리뷰어는 codex 하나이고 이 세션은 검증·수정만 한다. 끝나면 「리뷰·검사·PR」 항목을 닫는다.

## 7. 최종 보고 — 다섯 절, 짧게

1. 목표 계약 대비 판정(수용 기준마다 됐다/안 됐다)
2. 만든 것(파일:줄)
3. /review-loop 보고 요지(발견 · 반영 · 보류 · 검사 · PR)
4. 못 한 것과 사람이 할 것
5. 있었던 일(예상 밖의 것 · 되돌린 것 · 측정값). 「특이사항 없음」으로 채우지 마라

보고 뒤 `plan.md` 의 상자가 전부 닫혔는지 확인한다. 자원 회수 항목이 있으면 그것도 닫는다.

## 하지 마라

- 승인 전에 코드를 고치지 마라. 1~4단계는 읽기와 계획 파일 쓰기뿐이다. 「시작」이라는 사람의 말 없이 `plan.md` 를 쓰지 마라.
- 내장 `/code-review` 를 부르지 마라(리뷰는 /review-loop 안의 codex 하나 — Claude 토큰을 아끼려는 사용자 결정).
- 반영 뒤 다시 리뷰를 돌리지 마라. 한 단계에 한 사이클이다.
- 스스로 `/go` 를 다시 부르지 마라. 재개는 사용자가 인자 없이 친다.
